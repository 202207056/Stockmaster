# 학습 기능 프론트 업데이트에 따른 백엔드 요청사항

2026-09-15 · 제안 계약 · 이번 작업에서는 백엔드 코드·DB·배포를 변경하지 않음

구현 화면과 판단은 [프론트 구현기록](./2026-09-15_학습화면_구현_및_판단기록.md)을 참고한다. 아래 경로는 신규 제안이며 현재 호출되는 API가 아니다. 팀 합의 후 기존 API 명세에 반영한다.

## 1. 우선순위와 현재 화면의 제한

| 우선 | 백엔드 작업 | 연결할 화면 | 완료 시 달라질 동작 |
|---|---|---|---|
| P0 | 학습 시도·진도 저장 | 학습 홈·문제·코스 | 다른 기기에서도 같은 진도, 서버 기준 첫 시도·재시도 관리 |
| P0 | 계좌별 판단 초안·원본·수정 이력 | Trading·Assets 판단 노트 | 개인 서버 보존, 사용자/계좌 소유권 검증 |
| P0 | 판단 초안과 주문 ID 연결 | 주문 직후·주문내역 복기 | 종목의 현재 메모와 특정 주문 당시 근거를 구분해 조회 |
| P0 | 같은 시점 시세·잔고·주문 전후 스냅샷 | 예상 비중·체결 결과 비교 | 기준시각·예상/확정 상태가 있는 금액·비중·수량 표시 |
| P1 | 원가 배분·비용·실현손익·남은 평가손익 | 거래 복기 타임라인 | 추가 매수·부분 매도·전량 매도에서도 정확한 손익 |
| P1 | 선택 계좌 기반 코칭·캐시·수업 추천 | StockCoach·복기 | 다른 계좌나 이전 주문의 설명이 섞이지 않음 |
| P2 | 날짜 재검토 안내·구조화 조건 | 보유 중 점검 | 사용자가 정한 점검 시점의 화면 내 안내 |

## 2. 콘텐츠·시도·진도

현재 콘텐츠는 `frontend/src/constants/learningContent.js`에 있다. `CONTENT_VERSION=1`, 수업 ID A1~E3, 문제 ID A1-q1 등, 문맥 문제 ID context-1~6이다. 발행 전 설명과 정답을 검수한다.

- `GET /api/learn/courses`, `GET /api/learn/lessons/{lesson_id}`: 제목·목표·상황·실습 종류·가정·콘텐츠 버전·문항. 정답 채점은 서버가 담당한다.
- `POST /api/learn/attempts`: `{client_attempt_id, question_id, content_version, selected_option}`. 서버는 로그인 사용자, 정답·최초 시도, 재시도 번호를 결정한다. 동일 client_attempt_id 재전송은 같은 결과를 반환한다.
- `GET /api/learn/me/progress`, `PUT /api/learn/me/progress/{lesson_id}`: 현재 단계, 과정 완료, 버전. “완료”는 학습 과정 확인이며 투자 숙련도 판정과 분리한다.
- 오류: 미발행/버전 불일치 409 또는 명확한 오류 코드, 유효하지 않은 선택지 422, 권한 없는 개인 기록 403/404 정책 통일.
- 기기 기록 업로드는 사용자가 선택한 이후 수행한다. guest 기록을 로그인 계정에 자동 흡수하지 않는다. 문항 버전이 다르면 과거 시도 보존과 새 콘텐츠 진도를 구분한다.

완료 확인: 같은 요청 재시도 시 시도 수 중복 증가 없음, 다른 사용자 기록 접근 불가, 이전 콘텐츠의 첫 시도 이력 보존, 읽기 완료와 문제 정답률 구분.

## 3. 판단 기록·수정 이력

- `POST /api/learn/decisions`: 선택 계좌·종목·매수/매도 구분, 근거, 출처 메모, 불확실한 점, 재검토 조건. 서버 생성 draft_id/created_at 반환.
- `GET /api/learn/decisions?account_id=&symbol=`: 원본과 revision 목록. 사용자·계좌 소유권 확인.
- `POST /api/learn/decisions/{id}/revisions`: 유지/수정/보류·변경 이유·새 정보. 원문을 덮어쓰지 않는다. 낙관적 버전 검증으로 다른 탭 수정 충돌을 알린다.
- 명시적인 사용자 삭제 기능을 제공한다. 원본 불변은 편집 규칙이지 사용자 삭제를 막는 정책이 아니다.

필드 초안:

```json
{
  "decision_id": "server-generated-id",
  "account_id": 12,
  "symbol_code": "005930",
  "side": "매수",
  "reason": "확인한 근거",
  "evidence": "자료 제목·출처·발행 시각",
  "uncertainty": "더 확인할 점",
  "review_condition": "사용자가 다시 살펴볼 조건",
  "created_at": "2026-09-15T03:00:00Z",
  "version": 1,
  "revisions": []
}
```

자유 문장의 재검토 조건을 자동 충족 판정하지 않는다. 날짜 기반 안내부터 지원하고, 가격 임계값 등 구조화 가능한 조건만 나중에 확장한다.

## 4. 주문과 판단 연결 — 거래 재전송 금지

현재 UI는 주문 함수에 학습 저장을 넣지 않았다. 특정 주문 당시 근거를 만들기 위해 다음 중 팀이 정한 방식을 계약한다.

1. 주문 전 decision_id를 생성한다.
2. 기존 주문 요청에 선택형 decision_id를 포함하거나, 주문 성공 후 소유권 확인을 거쳐 전용 연결 API를 호출한다.
3. 전자 방식이면 서버가 주문 처리 시 해당 버전의 근거 참조를 보존한다. 후자 방식이면 연결 시각과 결정 원문의 작성 시각을 보존하고 “주문 전 기록” 여부를 검증한다.
4. `GET /api/learn/reviews/orders/{order_id}`에서 연결된 원문과 현재 작성한 사후 메모를 구분해 반환한다.

주문 성공·학습 저장 실패는 별도 상태로 반환한다. 실패한 메모만 재시도하며 주문 API를 다시 보내지 않는다. 결과 불명 상태에서는 주문내역/서버 식별자로 체결을 먼저 확인한다. `orders:changed` 브라우저 이벤트는 재조회 신호일 뿐 체결 증거가 아니다.

계획 하나에 추가 매수·부분 매도 등 여러 주문이 연결될 수 있다. 종목과 날짜만 같다고 기존 주문들을 자동으로 같은 계획에 묶지 않는다. 부분 체결 도입 시 order_id와 execution_id를 구분한다.

## 5. 주문 미리보기·스냅샷

현재 Trading에는 조회 가격과 현금만 있어 예상 거래금액·매수 후 현금만 표시한다. 실제 계좌 비중·매도 후 잔여 수량·과거 자산 변화는 빈값으로 안내한다.

필요 응답:

- account_id, symbol_code, side, requested_quantity
- quote_price, quote_as_of, account_as_of, 계산된 예상 거래금액·잔여 현금·잔여 수량·주문 전후 해당 종목 비중
- 계산의 비용 포함 여부와 비용값, estimated/confirmed 구분, 데이터가 불완전하면 null과 reason
- 체결 직전·직후 snapshot_id, execution/order 참조, 실제 체결가·수량·시각

시세와 전체 보유종목 평가액이 서로 다른 시점이면 그 차이를 표시할 수 있어야 한다. 현재가 0으로 시세 누락을 표현하지 않는다. 요청 수량은 양의 정수이고 잔고 부족·초과 매도 검증은 서버에서 한다. 미리보기 결과가 실제 체결을 보장하지 않는다.

## 6. 거래별 손익·복기

`GET /api/learn/reviews/orders/{order_id}` 또는 계획 기준 review 조회에서 다음을 제공한다.

- 원문·수정 이력·각 주문/체결의 실제 시간순 목록
- 취소·실패·체결 대기·일부 체결·체결 완료 상태
- 매도분 원가, 배분 방법, 수수료/세금, 실현손익
- 남은 수량·평균원가·평가 기준시각·남은 평가손익
- 사용자 사후 회고와 다음 확인 사항, 연관 수업 및 추천 이유

원가 배분은 BE·팀 회계 정책으로 확정한다. 평균원가 등 사용 방법을 응답에 명시하고 금액 계산은 Decimal로 수행한다. 금액 전송 타입은 기존 API 정책과 맞춰 문서화하며 프론트에 float 계산을 맡기지 않는다. 전량 매도 후 포트폴리오 행이 사라져도 과거 체결/원가/학습 기록은 보존돼야 한다.

검산 시나리오: 10,000원 × 30주 단일 매수 → 9,000원 × 10주 매도. 비용 제외 실현손익 −10,000원, 남은 20주 평가손익 −20,000원. 매도 전후 가격이 같으면 현금+평가액 합계는 동일하다. 여기에 추가 매수·다회 매도·전량 매도·비용 포함 케이스를 확대한다.

## 7. AI 연결

현재 StockCoach는 첫 계좌 기준·최대 3분 캐시 안내가 있다. 새 코칭은 account_id + symbol + stage + decision_version + execution/snapshot_id를 입력과 캐시 키에 포함한다. 로그인 사용자의 계좌 소유권을 확인하고 새 사건·수정 후 캐시를 무효화한다.

출력은 확인된 사실, 사용자 근거 요약, 회고 질문 1개, 관련 수업 ID 1개와 추천 이유로 제한한다. 출력 수업 ID는 발행 목록과 검증한다. 계산·주문 허용·정답 판정은 서버의 결정적 로직으로 처리한다. AI 장애 시 기본 질문·해설로 응답하며 타임아웃을 주문 처리에 전파하지 않는다.

## 8. 인수 테스트와 프론트 전환

1. 사용자·계좌 변경 시 다른 기록이 한 프레임이라도 섞이지 않는지 FE와 함께 확인.
2. 같은 사건의 중복 전송, 저장 충돌, 삭제, 서버 시간/타임존, 페이지 재진입 확인.
3. 주문 성공/메모 실패, 메모 성공/주문 실패, 주문 결과 불명 상태를 각각 검증.
4. 추가 매수·일부 매도·전량 매도 손익과 스냅샷 비교.
5. 서버 배포 준비 후 `useLearning`의 저장 경계를 어댑터로 교체한다. 화면에서 아직 기기 기록인지 서버 동기화인지 명시한다.
6. 기존 모의 주문 활성화 플래그는 학습 기능 추가만으로 바꾸지 않는다.
