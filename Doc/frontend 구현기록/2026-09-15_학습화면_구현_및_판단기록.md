# 학습 화면 구현 및 판단 기록

작성: 2026-09-15 · 브랜치: dev · 개발 전 기준 커밋: `8b1f0d4`

## 1. 요청과 범위

- 개발 전에 현재 진행 내용을 커밋하고, 최신 14·15번 기능 설계에 따라 프론트엔드 화면을 구현한다.
- 백엔드는 수정하지 않는다. 필요한 백엔드 작업은 [별도 인계 문서](./2026-09-15_학습기능_백엔드_요청사항.md)에 정리한다.
- 코스는 여러 학습 콘텐츠 중 하나이며 기본 화면의 주인공으로 두지 않는다.
- 기존 헤더·주 메뉴·푸터·디자인 토큰·전체 레이아웃·API와 주문 제출 로직을 유지한다.

작업 전 프론트와 백엔드 Git 작업 트리는 깨끗했다. 프론트의 기존 코드 작업은 `44dec1e`에 이미 커밋되어 있었고, 이번 대화에서 만든 설계 문서 3개는 `Doc/자료/`가 ignore 대상이라 추적되지 않았다. 해당 3개만 `git add -f`로 추가해 `8b1f0d4`에 기준점을 만들었다. ignore 규칙을 넓게 풀거나 환경파일·다른 로컬 문서를 일괄 포함하지 않았다.

## 2. 구현한 화면

| 위치 | 추가된 사용자 경험 | 데이터 범위 |
|---|---|---|
| `/learn` 추천 활동 | 보유 비중 비교·문장 속 개념 찾기를 바로 조작, 가상 거래와 선택형 코스 진입 | 교육용 고정 자료 |
| 짧은 실습·퀴즈 | 계좌 A/B 비중·공통 등락 조절, 문장 6개, 최근 답변이 오답인 문제 다시 확인 | 브라우저 시도 기록 |
| 선택형 코스 | 5개 코스·15개 수업, 상황→실습→확인 문제→다음 적용의 4단계 | 수업별 2문항, 총 30문항 |
| 가상 거래 복기 | 근거·재검토 조건→가상 체결→계획 점검→0/10/20/30주 선택→복기 | 실제 계좌와 분리된 가상 시나리오 |
| 도움말·용어 검색 | 기존 검색·카테고리·설명·예시·관련 용어를 보존 | 기존 glossary 데이터 |
| Trading 주문 아래 | 접이식 ‘거래 중 학습 도움’, 조회 가격 기준 예상금액·매수 후 현금, 종목 판단 기록 | 기존 화면의 조회값 + 계좌별 기기 메모 |
| Trading 주문내역 | `체결` 상태 주문에 ‘돌아보기’, 사후 복기·다음 확인 사항 기록 | 기존 주문 조회 결과 + 주문 ID별 기기 메모 |
| Assets 보유종목 아래 | 접이식 계획 점검, 최초 기록과 수정 이력 | 계좌·종목별 기기 메모 |

계산 실습은 현금·총자산, 지정가 조건, 호가 단계, 부분 매도, 하락 후 회복, 추가 매수 평균단가, 보유 비중, 가상 충격 시나리오를 다룬다. 뉴스·지표·판단 수업은 자료 선택과 근거 작성을 다룬다. 기사·판단 실습에서 작성한 내용을 사용자가 버튼으로 가상 판단 메모에 가져올 수 있다.

## 3. 개발 중 판단과 이유

### 3-1. 디자인을 새로 만들지 않음

`index.css`, `App.css`, 공통 Layout/Header/Footer/Nav를 변경하지 않았다. 기존의 `rounded-xl border-gray-200 p-4`, brand 계열 버튼, gray 배경, 한국식 상승/하락 색상과 폰트를 재사용했다. HTML 문서의 사이드바·큰 제목 디자인을 앱에 이식하지 않았다. 학습 본문만 확장하고 거래·자산은 기존 내용 아래에 접을 수 있는 영역을 붙였다.

### 3-2. 프론트 화면만 구현하되 실제 클릭 가능한 상태로 제공

아직 없는 API의 성공 응답을 꾸미는 대신 콘텐츠·가상 계좌·진도·개인 메모는 로컬 상태로 동작하게 했다. 가상 자료임을 표시하고 실주문 함수와 연결하지 않았다. 새 패키지는 설치하지 않았으며 기존 React/Tailwind/Router와 Node 테스트를 사용했다.

### 3-3. 코스는 선택 사항, 콘텐츠는 15개 전체 화면 제공

설계의 단계적 출시 순서는 유지할 수 있지만 이번 요청은 설계 기반 화면 구현이므로 15개 수업을 모두 탐색·실습 가능한 형태로 만들었다. 각 수업에 2문항을 작성해 총 30개, 독립 문맥 퀴즈 6개를 별도로 제공했다. 기존 설계의 첫 확장 6개/12문항보다 전체 화면 범위를 넓힌 것이다. 백엔드 발행 콘텐츠로 사용하기 전 팀 콘텐츠 검수가 필요하다.

수업 ‘완료’는 문제 2개에 응답하고 과정을 확인했다는 뜻이다. 정답률이나 투자 숙련도 판정과 구분한다. 문제 재시도 시 최초 정답 여부와 시도 횟수를 보존한다. 매수·매도·보유라는 선택 자체는 채점하지 않는다.

### 3-4. 실제 주문 로직에 학습 저장을 끼워 넣지 않음

기존 `place()`의 제출·토큰 확인·금액 검사·중복 제출 방지·결과 불명 처리·새로고침을 변경하지 않았다. 학습 버튼은 모두 `type="button"`이며 주문 `<form>` 밖에 있다. 종목 메모를 저장해도 주문은 전송되지 않는다. 주문 처리 중과 결과 불명 상태에서는 판단 입력 영역도 잠근다.

메모를 특정 주문 당시의 근거로 자동 연결하려면 서버 초안 ID·order_id 연결 계약이 필요하다. 지금은 **현재 종목 판단 노트**와 **사후 주문 복기**를 따로 표시한다. 과거 매수 이유를 현재 메모에서 역으로 만들어 넣지 않는다.

### 3-5. 금액·비중 표시의 한계는 UI에 드러냄

실제 Trading 화면에는 현재 조회 가격·수량·계좌 현금이 있어 예상 거래금액과 매수 후 현금은 표시할 수 있다. 같은 시점의 계좌 전체 평가액·보유 수량이 없으므로 실제 종목 비중과 매도 후 잔여 수량은 이 패널에서 임의 계산하지 않았다. 시세 기준시각도 없어 지연 여부를 확인할 수 없다고 안내한다. 가상 실습에서는 가정이 완전하므로 비중·일부 매도·손익을 모두 보여 준다.

실제 거래별 손익은 원가 배분·비용 계약이 없으므로 표시하지 않는다. 이미 체결된 주문의 사실과 사용자가 지금 작성한 복기만 보여 준다. 기존 StockCoach의 첫 계좌 기준·최대 3분 캐시 결과를 주문 계산에 재사용하지 않았다.

### 3-6. 사용자·계좌별 브라우저 기록

`stockmaster.learning.v1:guest`, `...:user:{id}`, `...:user:{id}:account:{accountId}`로 분리했다. 학습·가상 시나리오는 사용자 단위, 실제 종목 메모·사후 복기는 계좌 단위다. 사용자·계좌·종목을 React key에도 반영해 입력 중인 다른 계좌의 텍스트가 다음 계좌로 넘어가지 않게 한다. 로그인 시 guest 기록을 자동 병합하지 않는다.

저장 차단·용량 오류는 메모리 상태를 유지하며 “이번 방문 동안만 유지”를 표시한다. 잘못된 JSON·버전은 앱 전체를 중단하지 않는다. 기록에는 스키마 버전이 있으며 최대 500개 항목, 종목 점검 이력은 최근 50개를 유지한다. 삭제 UI는 학습 기록·종목 메모·사후 복기에 각각 제공한다. 브라우저 기록은 보안 저장소가 아니므로 다른 기기 동기화 및 서버 보존이 필요하면 백엔드 연결 작업을 진행한다.

### 3-7. 기존 용어집은 보조 기능으로 보존

기존 Learn의 용어 검색 컴포넌트를 `GlossaryBrowser`로 옮겼다. 검색·관련 용어 연결은 그대로이며 새 암기 콘텐츠는 추가하지 않았다. 학습 홈에서 작은 ‘도움말·용어 검색’ 링크로 들어간다.

## 4. 파일 구성

- `pages/Learn.jsx`: 추천 활동·실습·복기·코스·도움말 진입.
- `constants/learningContent.js`: 5개 코스/15개 수업/30문항/문맥 6문항의 버전별 콘텐츠.
- `components/learn/AllocationPractice`, `InteractivePractice`, `ContextQuestion`, `CourseLessons`, `TradeScenario`: 학습과 가상 실습.
- `DecisionNotebook`, `TradingLearning`, `OrderReflection`, `HoldingLearning`: 실제 화면의 선택형 기록 UI.
- `LearningUI`, `GlossaryBrowser`: 기존 스타일 재사용 및 보조 검색.
- `utils/learning`, `learningStore`, `hooks/useLearning`: 교육용 계산, 스코프 분리, 로컬 저장 구독.
- `pages/Trading`, `pages/Assets`: 새 영역 연결. 기존 API·주문 로직 보존.

## 5. 검증

- `npm.cmd test`: 30개 통과. 비중 0/100%·보합, 부분 매도 손익 보존, 최초/재시도 구분, 계좌·사용자 분리, 저장 실패·잘못된 데이터, 15개 수업 렌더, 기존 API·비로그인 경로를 확인했다.
- 테스트에서 현금만 보유한 계좌의 `-0`을 발견해 계산 모델에서 0으로 정규화했다.
- ESLint와 프로덕션 빌드 통과. 최종 변경 후 동일 검사를 재확인했다.
- 브라우저: 실제 개발 서버에서 학습 홈, 오답 해설, 가상 매수 근거→보유 점검→부분 매도→복기, 새로고침 후 기록 유지, D1 실습→확인 문제를 확인했다.
- 데스크톱과 390px 화면을 확인했다. 학습 본문에 화면 너비를 넘는 요소가 없었고, 기존 헤더의 가로 스크롤 동작은 유지했다.
- 서버 요청 없는 임시 개발 화면에서 판단 원본 저장·수정 이력, 계좌 A→B 분리·A 복귀 시 기록 복원, 주문 사후 복기 저장·삭제를 직접 확인했다. 검증용 입력과 임시 화면 파일은 제거했다.
- 배포 백엔드의 신규 학습 API·실제 주문 실행은 검증하지 않았다. 계정 생성·실주문·백엔드 변경을 하지 않았다.

## 6. 백엔드 연결 전 남는 차이

기기 기록만 저장되므로 서버 로그인 세션과 기기간 동기화는 없다. 실제 주문 전/후 스냅샷, 과거 계획 자동 연결, 거래별 원가 배분과 확정 손익, 시세 시각, 계획 재검토 알림, 새로운 학습 추천 API는 구현하지 않았다. 화면에서 확인 불가·준비 중으로 구분하고 [백엔드 요청사항](./2026-09-15_학습기능_백엔드_요청사항.md)에 계약을 남겼다.
