# 예약·조건 주문 분석 및 Stockmaster 설계

작성일: 2026-10-06. 구현 전에 작성한 기능 분석과 구현 계약이며, 검증 결과는 문서 마지막에 추가한다.

## 1. 조사 범위와 공식 근거

KB증권 M-able은 모바일 MTS이며 PC HTS는 H-able이다. 화면 배치는 H-able의 종목·주문·잔고·미체결 영역 구성을 참고하고, 기능은 아래 공식 자료에서 확인했다. 과거 도움말의 운영 시간이나 한도를 현재 모든 상품에 적용하지 않는다. 로그인한 M-able 실제 화면을 직접 실행한 조사는 아니다.

| 공식 자료 | 확인한 내용 | 적용 판단 |
|---|---|---|
| [KB증권 매체 안내](https://m.kbsec.com/go.able?linkcd=m10030000) | H-able과 M-able 매체 구분 | 웹의 반응형 화면으로 재구성 |
| [KB증권 최선집행기준 설명서, 2025-11-24 시행, 7쪽](https://www.kbsec.com/Board/notice/data/202511/251121_1763680306685.pdf) | 국내 예약주문은 장개시 전 동시호가/시간외종가 주문 예약이며 번호 순서로 KRX 접수. 서버 자동주문은 시세 조건을 감시하여 주문 처리 | 예약 등록과 실제 주문 실행을 분리하고 서버 감시 사용 |
| [KB H-able 0913 주식파워트레이딩2 도움말](https://help2.kbsec.com/pdf/0913.pdf) | 종목 정보·주문·잔고 및 미체결 조회를 한 화면에서 연결 | 트레이딩 화면에 등록과 관리 영역 배치 |
| [키움 영웅문 주식 자동감시주문 0624](https://download.kiwoom.com/flash_help_new/0624.htm) | HTS 종료 후에도 서버 감시. 조건 가격·주문 가격·수량·유효기간을 구분. 익절·손절과 트레일링 스탑, 감시 시작·중지 제공 | 브라우저 타이머 대신 DB에 저장한 서버 작업. 가격 이상/이하 조건과 만료부터 지원 |
| [삼성증권 POP 2108 예약주문 도움말](https://www.samsungpop.com/contents/popdts/help/2108.html) | 일반 1회 예약, 기간별 반복 수량, 목표 총수량 예약을 구분. 예약현황 취소와 일별 실행내역 제공 | 첫 버전은 1회 예약. 반복 주문은 별도 기능으로 남김 |

실제 증권사의 예약은 주로 다음 거래일 주문 접수 서비스다. 아래 Stockmaster의 날짜·시간 지정 예약은 학습용 제품 결정이며 KB 기능의 동일 복제가 아니다. 조건주문은 거래소의 **조건부지정가**(장 마감 시 시장가 전환)와도 다르다.

## 2. 용어와 사용자 경험

| 방식 | 시작 기준 | 등록 시 잔고 | 결과 |
|---|---|---|---|
| 일반 시장가 | 지금 주문 확정 | 즉시 반영 | 기존 서버 현재가 모의 체결 |
| 기존 지정가 | 지정 가격으로 접수 | 변동 없음 | 기존 `대기`, 자동 체결 기능 없음 |
| 예약 주문 | 한국시간 실행 시각 이후 | 변동/예약 없음 | 유효기간 내 감시 시간에 첫 유효 시세로 1회 시장가 실행 |
| 조건 주문 | 현재가 ≥ 또는 ≤ 감시 가격 | 변동/예약 없음 | 유효기간 내 조건을 처음 확인하면 1회 시장가 실행 |

예시: 50,000원 이하 매수, 55,000원 이상 매도(익절), 45,000원 이하 매도(손절). 감시 가격은 체결 보장 가격이 아니다. 시세를 확인한 순간의 가격으로 모의 체결하고 기존 수수료·세금을 반영한다. 각 조건은 독립 주문이다. 익절·손절을 둘 다 만들더라도 한쪽 체결 시 다른 쪽을 자동 취소하는 OCO는 제공하지 않는다.

입력 → 등록 내용 확인 → 서버 등록 → 예약대기/감시중 → 체결/거부/만료/취소 순서로 표시한다. 등록을 체결 완료라고 부르지 않는다. 같은 계좌의 목록에서 조건, 시각, 최근 확인, 중단 사유, 생성된 주문번호를 확인하고 실행 전 취소할 수 있다. 계좌를 바꾸면 해당 계좌 데이터만 조회한다.

## 3. 첫 구현 범위

- 국내 종목의 모의 현금 매수·매도, 정수 수량, 1회 실행.
- 예약: 미래 날짜·시간을 한국시간으로 입력. 조건: 가격 이상/이하. 만료는 두 방식 모두 필수이며 최대 30일(Stockmaster 자체 제한).
- 계좌당 활성 등록 최대 20건. 내역은 활성 등록을 먼저 표시하고 최근 종료 내역을 합쳐 최대 200건 조회한다.
- 실행 방식은 시장가만 지원. 미체결 지정가 엔진이 없는 상태에서 지정가 실행을 지원한다고 표시하지 않는다.
- 서버는 약 30초 간격으로 확인한다. 감시 범위는 평일 09:00~15:20 KST의 학습용 접속매매 시간이다. 최근 당일 분봉의 날짜·시각·가격을 확인하고 2분보다 오래된 시세는 사용하지 않는다. 따라서 주말, 휴장일, 거래정지, 지연 시세에서는 체결을 만들지 않는다. 장중 거래가 드문 종목은 실행이 지연될 수 있다.
- 예약 시각이 장외이면 유효기간 내 다음 유효 시세를 기다린다. 만료가 먼저 오면 실행하지 않는다. 서버 중단 중 놓친 조건을 과거 데이터로 소급 체결하지 않는다. 재시작 후 DB의 활성 작업을 다시 확인한다.
- 실행 시 현금·보유 수량을 다시 검사한다. 부족하면 `거부`로 끝내고 자동 재주문하지 않는다. 시세/통신 장애는 활성 상태를 유지하고 이유를 표시한 뒤 만료까지 재확인한다.
- 서버가 계속 실행되는 환경이 필요하다. 무료 호스팅의 휴면 중에는 감시할 수 없다. 화면에는 운영 서버의 감시 가능 여부와 마지막 작업 확인 시각을 표시한다.
- 반복 예약, 부분 체결, OCO, 트레일링 스탑, 비율 조건, 알림 전송, 신용/미수/파생/해외/NXT, 거래소의 실제 주문 전송은 범위 밖이다.

## 4. 서버 구조와 API

기존 `orders`를 감시 설정 저장소로 재사용하지 않고 `order_automations`를 추가한다. 자동 실행 성공 시 기존 `orders`에 체결 1건을 생성하고 연결한다. 기존 주문 API·학습 예시는 유지한다.

| API | 용도 |
|---|---|
| `GET /api/trading/automations/capabilities` | 감시 실행 여부·최근 작업 시각·간격·시간대·지원 기능 |
| `POST /api/trading/automations` | 본인 계좌에 예약/조건 등록. `client_request_id`로 재시도 중복 방지 |
| `GET /api/trading/automations?account_id=` | 본인 계좌의 등록 및 종료 내역 |
| `PUT /api/trading/automations/{id}/cancel` | 활성 작업 취소, 반복 취소는 동일 결과. 체결 이후 취소 불가 |

공통 입력: `account_id`, `symbol_code`, `order_type`, `quantity`, `kind` (`scheduled`/`condition`), `expires_at`, `client_request_id`.
예약 추가 입력: `scheduled_at`. 조건 추가 입력: `trigger_operator` (`gte`/`lte`), `trigger_price`.
시간은 offset이 있는 ISO 8601로 받아 UTC 저장하고, 화면은 명시적으로 Asia/Seoul로 표시한다.
서버는 불필요한/상충하는 조건 필드를 거부한다. 수량·가격·유효기간·계좌 소유권과 종목 존재를 검사한다.

작업에는 등록 시각, 최근 확인 시각·가격, 상태 사유, 실행 시각, 생성 주문 ID를 저장한다. 등록 응답과 목록에는 같은 구조를 사용한다. 등록만으로 현금/보유량/수수료를 차감하지 않는다.

### 원자성과 장애 처리

작업 실행 시 DB 작업 행 잠금 후 상태·만료·조건을 다시 확인한다. 같은 트랜잭션 안에서 계좌를 잠그고 기존 체결 처리를 호출하여, 잔고 변경·체결 주문 생성·작업 종료를 한 번에 커밋한다. 작업 상태를 먼저 저장하고 별도 HTTP 주문을 호출하는 방식은 사용하지 않는다. 여러 워커의 중복 실행과 취소 경쟁은 같은 행 잠금으로 직렬화한다. 시세 API 요청 동안 DB 잠금을 잡지 않는다.

사용자 계좌 단위 등록 멱등키를 둔다. 같은 키로 다른 내용을 보내면 409. 확인 전에는 전송하지 않고 통신 결과가 불명확할 때 같은 키로만 재확인한다. 운영 비밀키·JWT는 작업 테이블에 저장하지 않는다.

## 5. 화면 구성

트레이딩 화면의 기존 주문/차트 아래에 `예약·조건 주문` 영역을 배치한다. 선택 종목과 계좌를 공유하고, `예약 주문`/`가격 조건` 선택 후 매수·매도, 수량, 시각 또는 가격, 만료를 입력한다. 확인 영역에는 사람이 읽을 수 있는 한 문장, 기준 시세에 따른 예상 수수료·입출금, 실행 시 재검증 안내를 표시한다.

감시 내역은 가로 스크롤 가능한 표로 제공한다. 계좌 선택, 상태 배지, 최근 확인 시각, 사유, 취소 버튼을 제공하고 화면을 보고 있을 때만 주기적으로 조회한다. 프론트 조회를 멈춰도 서버 감시는 계속된다. 기존 서버가 신규 API를 지원하지 않거나 운영 감시가 중단된 경우 등록 성공처럼 보이지 않게 사용 불가 상태를 표시한다. 기존 `VITE_ENABLE_ORDER_SUBMISSION` 설정을 따른다.

## 6. 배포 및 검증 계획

1. 독립 개발 DB에서 신규 Alembic revision 적용. 운영 DB 마이그레이션은 별도 배포 시 수행.
2. 백엔드 배포 후 감시 프로세스 활성화 및 capabilities 확인. 계속 실행되는 인스턴스와 시세 키 준비.
3. 프론트 배포 및 주문 전송 설정 확인. 두 저장소의 변경을 함께 반영해야 한다.
4. 오프라인 테스트: 입력 오류/시간대/30일 제한, 계좌 소유권, 멱등성, 이상·이하 경계, 예약 시각·만료, 오래된 시세·장외, 수수료·잔고·보유량, 실행 1회, 취소, 재시작 후 재조회.
5. 프론트 테스트: 확인 전 미전송, 정확한 JSON과 KST 변환, 계좌 전환, 등록/거부/만료/취소 구분, 기존 API 미지원, 기존 일반 주문·튜토리얼 회귀.

실제 운영 서버에서 주문을 생성하거나 운영 DB를 변경하는 검증은 이 로컬 구현에 포함하지 않는다.

## 7. 구현 결과 및 배포 절차

### 변경 위치

- 프론트: `frontend/src/components/common/AutomationOrders.jsx`, `src/utils/orderAutomations.js`, `src/api/data.js`, `src/pages/Trading.jsx`.
- 백엔드(별도 `gp-mock-inv` 저장소): `app/models/order_automation.py`, `app/schemas/order_automation.py`, `app/routers/order_automations.py`, `app/services/order_automation_service.py`, `app/main.py`, `app/config.py`.
- 기존 `create_order`에 트랜잭션을 외부에서 커밋할 수 있는 옵션을 추가했다. 일반 주문은 기존처럼 즉시 커밋한다.
- 새 Alembic head: `d20261006_automations` → 이전 `c4e8a1b27d90` 다음. 기존 주문 기록은 수정하지 않는다.

### 배포 순서

```powershell
# gp-mock-inv/backend: 대상 DB와 서버 환경을 확인한 후 배포 과정에서 실행
python -m pip install -r requirements.txt
alembic upgrade head
# 서버 .env: ENABLE_ORDER_AUTOMATIONS=true (기본 true)
# KIS 모의 시세 키 또는 실전 조회 키 준비. 실제 증권사 주문 API는 호출하지 않음.
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

새 테이블이 없으면 기존 서버 기능은 유지하고 자동 주문 감시만 시작하지 않는다. capabilities와 신규 API는 사용 불가 상태를 전달한다. migration을 서버 실행 중 적용했다면 재시작한다. `ENABLE_ORDER_AUTOMATIONS=false`이면 신규 감시는 멈추지만 저장된 작업은 삭제하지 않는다. 재활성화하면 아직 유효한 작업을 다시 확인하므로, 종료하려는 작업은 먼저 취소한다.

프론트는 기존 주문 전송 설정을 그대로 따른다. 대상 서버에 신규 API가 배포된 뒤 `VITE_ENABLE_ORDER_SUBMISSION=true`로 실행/빌드해야 등록할 수 있다. `VITE_` 환경변수에는 DB 접속 정보나 시세 비밀키를 넣지 않는다. 무료 서버가 휴면하면 감시도 멈추므로 항상 실행되는 서버를 사용한다.

### 검증 결과와 한계

- 프론트 전체 테스트 86개 통과: 한국시간 변환, 예약/조건 요청 구분, 확인 후 등록, 응답 유실 후 동일 멱등키 재확인, 취소, 구버전 서버 안내 및 기존 주문/튜토리얼/관심종목 회귀 포함.
- 백엔드 테스트 47개 통과: 예약·조건 테스트 19개와 기존 시세/뉴스 테스트 28개. 독립 SQLite DB에서 잔고/보유량/수수료, 1회 실행, 취소, 만료, 소유권, 멱등성, 원자적 롤백 후 재실행, 시세 오류, 감시 상태, 미등록 종목 조회, 신규 migration upgrade/downgrade 검증.
- 프론트 ESLint·프로덕션 빌드 통과. 번들 500kB 초과 경고는 남아 있으며 이번 기능의 실행 오류는 아니다.
- PostgreSQL의 실제 다중 프로세스 경합은 운영 DB에서 실행하지 않았다. `SELECT … FOR UPDATE`로 작업 행과 계좌 행을 잠그는 구조이며 SQLite 테스트가 PostgreSQL의 행 잠금 동작까지 입증하는 것은 아니다.
- 체결은 호가 잔량을 소비하는 거래소 매칭이 아니라 최근 2분 이내의 거래량이 있는 당일 분봉 종가를 사용하는 모의 체결이다. 감시 가격을 잠깐 통과한 뒤 복귀하면 놓칠 수 있으며, 해당 시점의 실제 매수/매도 호가나 체결을 보장하지 않는다. 과거 시세로 소급 실행하지 않는다.
- 기존 `지정가 대기` 주문의 자동 체결은 이번 자동주문과 별개이며 여전히 제공하지 않는다.
- 실제 운영 주문·운영 DB 마이그레이션·배포는 실행하지 않았다.
