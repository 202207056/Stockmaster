# 팀원 API 연동 실행 가이드

작성 기준: 2026-09-08 작업 사본. Windows PowerShell 기준이며, 경로는 각자 내려받은 위치에 맞춘다.

이 문서는 팀원이 직접 프론트를 실행하고, 회원가입·로그인 후 실제 데이터 연결 여부를 확인하는 절차다. **화면 실행 성공, 로그인 성공, KIS 시세 조회 성공은 각각 따로 확인한다.**

## 1. 어떤 방식으로 실행할지 선택

| 목적 | 선택 | 필요한 것 |
|---|---|---|
| 연동된 프론트 화면 확인 | A. 로컬 프론트 + 팀 배포 백엔드 | 프론트 코드, Node.js/npm, 해당 서버의 계정 |
| 백엔드 코드 수정까지 확인 | B. 로컬 프론트 + 로컬 백엔드 | 두 저장소, Python, PostgreSQL 개발 DB, 기능별 외부 API 설정 |

처음 확인하는 프론트 팀원은 **방법 A**부터 진행한다. KIS API 키나 DB 비밀번호를 받을 필요가 없다. 해당 값은 백엔드 서버가 가지고 있어야 한다.

```text
브라우저의 프론트
  → VITE_API_BASE_URL에 지정된 백엔드
      → PostgreSQL: 회원·계좌·종목 기본정보·게시글 등
      → KIS 모의투자 API: 개별 종목 현재가·차트
      → KIS 실전투자 API: 종목 순위
```

프론트에서 DB에 직접 연결하지 않는다. 백엔드 폴더를 받는 것만으로 서버가 실행되거나 기존 DB 데이터가 복제되지 않는다.

## 2. 코드를 공유하는 사람과 받는 사람이 먼저 확인할 것

### 공유하는 사람

- 프론트의 변경 파일과 새 문서를 커밋하고 원격 브랜치에 push한다. `.env`와 비밀키는 포함하지 않는다.
- 팀원에게 저장소 URL, 사용할 브랜치, 확인할 커밋 ID, 백엔드 주소를 전달한다.
- 백엔드 변경이 있다면 코드 공유와 별도로 배포 서버에 반영됐는지 확인한다.

이번 문서 작업에서는 커밋·push·서버 배포를 수행하지 않았다. **작성자의 미커밋 변경은 팀원이 pull해도 받을 수 없다.**

### 처음 받는 사람

작업할 상위 폴더에서 실행한다. 저장소 접근 권한이 필요할 수 있다.

```powershell
git clone https://github.com/202207056/Stockmaster.git
```

방법 B를 사용할 때만 백엔드도 받는다.

```powershell
git clone https://github.com/202207048/gp-mock-inv.git
```

이미 받은 저장소에서는 먼저 현재 상태를 확인한다.

```powershell
cd Stockmaster
git status --short
git branch --show-current
git log -1 --oneline
```

로컬 수정이 있으면 보존한 뒤 진행한다. 공유받은 브랜치로 이동한 상태에서 최신 코드를 받는다. 브랜치명은 팀에서 전달받은 실제 이름을 사용한다.

```powershell
git fetch origin
git switch 전달받은_브랜치명
git pull --ff-only
git log -1 --oneline
```

`--ff-only`가 실패하면 로컬과 원격 이력이 갈라진 것이다. 강제 초기화하지 말고 담당자와 브랜치를 맞춘다. 프론트와 백엔드는 서로 다른 저장소이므로 방법 B에서는 각각 확인한다.

## 3. 방법 A — 프론트만 실행하고 팀 배포 서버 연결

### A-1. 실행 환경 확인

현재 프론트 검사는 Node.js 24 환경에서 수행했다. 같은 계열 환경을 맞추고 PowerShell에서 확인한다.

```powershell
node --version
npm.cmd --version
```

명령을 찾을 수 없으면 Node.js 설치와 PATH를 확인하고 터미널을 다시 연다. Windows에서는 PowerShell 스크립트 실행 정책 문제를 피하도록 아래 예시에서 `npm.cmd`를 사용한다.

### A-2. 의존성 설치 및 환경 파일 준비

`Stockmaster` 폴더에서 실행한다.

```powershell
cd frontend
npm.cmd ci
if (!(Test-Path .env)) { Copy-Item .env.example .env }
```

`npm.cmd ci`는 저장소의 잠금 파일을 기준으로 설치한다. 위 복사 명령은 기존 `.env`를 덮어쓰지 않는다. **기존 파일이 있으면 이전 API 주소가 남아 있을 수 있으므로 반드시 직접 확인한다.**

`Stockmaster/frontend/.env` 내용을 다음과 같이 맞춘다.

```dotenv
VITE_API_BASE_URL=https://gp-mock-inv.onrender.com/api
VITE_ENABLE_ORDER_SUBMISSION=false
```

- 주소 끝에 `/api`를 포함한다. `/docs`는 명세 페이지이므로 API 주소로 넣지 않는다.
- 프론트의 `VITE_` 변수는 브라우저에 노출된다. KIS 키, DB URL, JWT 서명키를 넣지 않는다.
- 주문은 현재 점검 때문에 기본 비활성화다. 연결 확인을 위해 임의로 `true`로 바꾸지 않는다.
- `.env`를 만들지 않으면 코드의 기본 주소인 `http://localhost:8000/api`로 요청할 수 있다.

### A-3. 프론트 실행

같은 `frontend` 폴더에서 실행한다.

```powershell
npm.cmd run dev
```

터미널에 출력된 `Local` 주소를 연다. 일반적으로 `http://localhost:5173`이지만 포트 사용 상황에 따라 달라질 수 있다. 해당 터미널을 닫으면 개발 서버도 종료된다. 종료는 `Ctrl+C`다.

`.env`를 수정했다면 `Ctrl+C` 후 `npm.cmd run dev`로 재시작하고 브라우저를 새로고침한다. `.env.local`, `.env.development`, `.env.development.local`에 같은 변수가 있으면 의도한 값이 덮어써질 수 있다. 최종 연결 주소는 6절의 Network에서 확인한다.

### A-4. 배포 백엔드 확인

브라우저에서 다음 주소를 연다.

- 상태: `https://gp-mock-inv.onrender.com/`
- API 명세: `https://gp-mock-inv.onrender.com/docs`

상태 응답에 `"status":"ok"`가 있으면 웹 서버가 응답한 것이다. **DB 접속이나 KIS 연동까지 성공했다는 뜻은 아니다.** 처음 응답이 느리면 잠시 기다린 뒤 한 번 다시 확인한다. 계속 실패하면 반복 새로고침보다 Network와 서버 로그를 확인한다.

## 4. 테스트 계정 생성 및 로그인

미리 만들어져 있다고 확인된 공통 테스트 계정은 없다. 팀에서 제공한 계정을 사용하거나 대상 서버에 직접 가입한다.

1. 실행한 프론트에서 `/signup`으로 이동한다.
2. 팀원별로 겹치지 않는 아이디·이메일을 사용한다. 아이디는 현재 프론트 기준 영문·숫자·밑줄 4~20자다. 예: `team01_0908`.
3. 이름, 사용할 비밀번호, 비밀번호 확인, 이메일을 입력한다. 예시 계정이 실제로 존재한다는 뜻은 아니다.
4. 가입을 제출한다. 현재 프론트는 회원가입 후 자동 로그인을 시도하고 설문으로 이동한다.
5. 우선 연결만 확인하려면 설문을 건너뛰고 `/dashboard` 또는 `/mypage`에서 로그인 정보를 확인한다.
6. `/assets`에서 기본 계좌를 확인한다. 현재 백엔드 가입 코드는 모의투자 기본계좌와 초기 예수금 10,000,000원을 생성한다. 기존 계정의 금액은 다를 수 있다.
7. 로그아웃한 뒤 `/login`에서 같은 아이디·비밀번호로 다시 로그인한다.

가입 정보는 `.env`가 가리키는 백엔드의 DB에 저장된다. 방법 A에서는 팀 배포 DB에 저장되며, 별도 로컬 DB에서 만든 계정은 배포 서버에서 자동으로 사용할 수 없다. 관심종목 목록은 현재 계정별 브라우저 로컬 저장소에 보관되므로 다른 PC에서 로그인해도 자동 동기화되지 않는다.

가입 응답이 성공했는데 자동 로그인이 실패한 경우에는 먼저 `/login`에서 로그인해 본다. 무조건 가입을 반복하면 이미 사용 중인 아이디 오류가 날 수 있다.

## 5. 화면별 연동 확인 순서와 통과 기준

로그인한 상태로 진행한다. 아래 순서대로 확인하면 DB 조회 문제와 외부 시세 문제를 구분하기 쉽다. API 경로는 모두 `/api` 기준이다.

| 순서 | 화면·행동 | 주요 API | 확인 기준 |
|---|---|---|---|
| 1 | 마이페이지 | `GET /users/me` | 가입한 사용자 정보 표시 |
| 2 | 내 자산 | `GET /trading/accounts`, `/trading/portfolio?account_id=...` | 본인 계좌·예수금 표시. 신규 계좌의 보유종목이 없는 것은 정상 |
| 3 | 트레이딩에서 `005930` 검색 | `GET /stocks?search=005930` | 종목 목록에 삼성전자 표시. DB에 해당 종목이 있어야 함 |
| 4 | 검색 결과에서 종목 선택 | `GET /stocks/005930` | 종목명·코드 표시 |
| 5 | 선택 종목 현재가 | `GET /stocks/005930/price` | 유효한 `current_price`가 화면에 표시 |
| 6 | 같은 종목 차트 | `GET /stocks/005930/chart?period=D` | 날짜와 OHLC 데이터가 있고 차트 표시 |
| 7 | 관심종목 담기 후 `/favorites` | 종목 상세·현재가 API | 담은 종목과 현재가 표시. 관심종목 저장 자체와 시세 조회 성공은 별개 |
| 8 | 홈 순위 | `GET /stocks/ranking/amount`, `/change`, `/volume` | 3개 영역에서 반환된 데이터 중 각각 최대 5개 표시 |
| 9 | 홈 뉴스·커뮤니티 | `GET /news/market`, `/community/posts` | 목록 표시 또는 실제 빈 응답에 따른 빈 상태 표시 |

게시글·댓글 작성과 설문 제출은 데이터를 저장하는 별도 확인이다. 공용 DB에서 수행한다면 테스트임을 식별할 수 있게 작성한다. 위 기본 조회 점검에는 작성이나 주문 제출이 필요하지 않다.

### 실패로 오해하지 말아야 할 현재 상태

- **상단 주요 시세 지표:** 해당 지표 API가 아직 없어 `— / 준비 중` 표시. 연동 성공 판정 대상에서 제외한다.
- **비로그인:** 화면을 열 수 있어도 보호된 데이터 조회는 제한된다.
- **시세·차트:** 모의투자 KIS 키를 사용한다. 홈 순위용 실전 키와 다르므로 순위가 나와도 시세·차트가 실패할 수 있다.
- **빈 순위:** 현재 백엔드는 키 미설정이나 일부 외부 요청 실패에도 빈 배열을 반환한다. 빈 목록만으로 정상이라고 판정하지 않는다.
- **시세 기준시각:** 응답에서 기준시각을 제공받지 못하므로 화면에 숫자가 나와도 실시간성까지 보증하지 않는다.
- **주문 버튼:** 기본 비활성화는 의도된 설정이다.

## 6. 실패한 API를 브라우저에서 확인하는 방법

1. 프론트 화면에서 `F12`를 누르고 **Network(네트워크)** 탭을 연다.
2. `Fetch/XHR` 필터를 선택한다. 화면 이동 후에도 기록을 보려면 `Preserve log`를 켠다.
3. 기록을 비우고 문제를 한 번 재현한다. 차트라면 `005930`을 선택한다.
4. `price`, `chart`, `stocks` 등 실패한 요청을 선택한다.
5. **Headers → Request URL**에서 실제 서버 주소와 `/api` 경로를 확인한다.
6. **Status Code**와 **Response**의 오류 본문을 확인한다. 요청에 `Authorization: Bearer ...`가 붙는지도 본인 화면에서만 확인한다.
7. 응답을 읽을 수 없다면 **Console**에서 CORS, 연결 거부, Mixed Content 등 관련 오류를 확인한다.
8. 요청 시각, 종목코드, URL의 경로, 상태 코드, 민감값을 제거한 메시지를 기록한다.

Authorization 값·비밀번호·쿠키를 공유하지 않는다. `Copy as cURL`이나 HAR에는 로그인 정보가 포함될 수 있으므로 원문 전체를 전달하지 않는다.

### 관심종목과 차트가 함께 실패할 때

관심종목의 `조회 실패 · 재시도`는 종목 상세와 현재가 오류를 구분하지 않는다. 먼저 `/stocks/005930`와 `/stocks/005930/price` 중 어느 요청이 실패했는지 확인한다.

`서버에 연결할 수 없습니다. 네트워크 상태를 확인해 주세요.`는 프론트가 읽을 수 있는 HTTP 응답을 받지 못했다는 의미다. 사용자 인터넷 문제로 확정할 수 없다. 주소 오류, 서버 연결 실패, CORS 차단 등을 구분해야 한다. 백엔드 내부 오류 응답에 CORS 헤더가 빠지는 상황도 확인 대상이다.

## 7. Swagger에서 같은 API를 직접 비교

프론트 문제인지 백엔드 처리 문제인지 구분할 때 사용한다. **프론트와 같은 서버의 `/docs`**를 열어야 한다.

1. `POST /api/users/login`을 펼치고 `Try it out`을 누른다.
2. 본인의 테스트 계정으로 아래 형태의 JSON을 입력하고 `Execute`한다. 값은 직접 바꾼다.

```json
{
  "login_id": "본인이_가입한_아이디",
  "passwd": "본인의_비밀번호"
}
```

3. 성공 응답의 `access_token`을 본인 브라우저에서 복사한다.
4. 상단 `Authorize`의 HTTPBearer 입력란에 **토큰 문자열만** 입력한다. `Bearer ` 접두사는 Swagger가 붙인다.
5. `GET /api/users/me`를 실행해 사용자 정보가 나오는지 확인한다.
6. `GET /api/stocks/{symbol_code}`에 `005930`을 넣고 실행한다.
7. 같은 코드로 `/price`와 `/chart`를 실행한다. 차트의 `period`는 `D`다.
8. 각 응답 코드와 본문을 프론트에서 실패한 요청과 비교한다.

| 비교 결과 | 다음 확인 |
|---|---|
| Swagger에서도 `/me` 실패 | 계정·JWT·DB 연결 확인. 이후 시세 진단보다 먼저 해결 |
| `/me`와 종목 상세는 성공, `/price`·`/chart`는 500 | 백엔드 로그에서 KIS 모의 토큰·외부 요청·응답 변환 예외 확인 |
| Swagger는 성공, 프론트만 실패 | 프론트 API 주소·로그인 헤더·실제 origin·CORS·실패 시각 차이 확인 |
| 종목 상세만 404 | `item_master`에 해당 코드가 있는지 확인 |
| 응답 200이지만 차트가 빈 배열 | KIS 설정과 외부 응답 확인. HTTP 성공과 데이터 존재 여부를 구분 |
| 차트 응답에 값은 있지만 화면이 비어 있음 | 날짜·양수 OHLC·고가/저가 범위를 확인. 프론트가 유효하지 않은 행을 제외함 |

Swagger 성공만으로 다른 origin의 프론트 CORS까지 검증되지는 않는다. 테스트가 끝나면 Swagger의 인증도 해제한다.

## 8. 방법 B — 백엔드와 DB까지 로컬 실행

프론트는 방법 A의 설치 절차를 사용하되 API 주소만 로컬로 바꾼다. 아래 백엔드 절차는 **새 독립 개발 DB** 기준이다. 기존 공용 DB의 마이그레이션·시드는 백엔드 담당자가 적용 상태를 확인한다.

### B-1. 준비 및 가상환경

Python 실행 환경과 PostgreSQL 서버를 준비한다. Python 3.11 환경을 시작점으로 사용할 수 있으나, 이 문서 작성 환경에서는 백엔드 신규 설치를 직접 검증하지 않았다. `python --version`으로 실행기를 확인한다. Windows에서 `python` 대신 `py`가 설정된 경우 가상환경 생성에 `py -3.11 -m venv .venv`를 사용할 수 있다.

터미널 1에서 `gp-mock-inv/backend`로 이동한다.

```powershell
cd gp-mock-inv/backend
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

가상환경 활성화 스크립트 없이 해당 Python 실행기를 직접 사용한다. 이후 명령도 이 폴더에서 실행한다.

### B-2. 개발 DB 생성

PostgreSQL이 로컬에서 실행 중이고 `psql` 명령을 사용할 수 있는 경우의 예다. `postgres` 관리자 계정 비밀번호는 로컬 설치 때 설정한 값을 입력한다. pgAdmin을 사용한다면 같은 이름의 사용자와 빈 DB를 UI에서 만들어도 된다.

```powershell
psql -h localhost -U postgres -d postgres
```

psql 안에서 실행한다. 이미 만든 사용자·DB라면 반복하지 않는다.

```sql
CREATE USER gp_dev WITH PASSWORD '본인이_정한_개발DB_비밀번호';
CREATE DATABASE gp_dev OWNER gp_dev;
\q
```

### B-3. 백엔드 `.env` 작성

`gp-mock-inv/backend/.env`를 새로 만들고 아래 형식으로 작성한다. 예시의 DB 비밀번호와 서명키는 실제 값으로 교체한다.

```dotenv
DATABASE_URL=postgresql://gp_dev:개발DB비밀번호@localhost:5432/gp_dev
SECRET_KEY=생성한_무작위_서명키
ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=60
KIS_APP_KEY=
KIS_APP_SECRET=
KIS_REAL_APP_KEY=
KIS_REAL_APP_SECRET=
GEMINI_API_KEY=
```

로컬 서명키는 아래 명령으로 생성한 값을 직접 넣을 수 있다. 출력된 값은 공유하지 않는다.

```powershell
.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(48))"
```

DB 비밀번호에 `@`, `:`, `/`, `%` 등 URL 특수문자가 있으면 연결 URL에 맞게 인코딩해야 한다. 현재 Alembic 설정의 `%` 처리 문제까지 발생한다면 백엔드 담당자에게 연결 설정을 확인받는다.

| 설정 | 용도 | 없을 때 |
|---|---|---|
| `DATABASE_URL`, `SECRET_KEY` | DB 연결, 로그인 토큰 서명 | 정상 실행·인증에 필요한 필수 설정 |
| `KIS_APP_KEY`, `KIS_APP_SECRET` | 모의투자 현재가·차트 | 키 미설정 시 현재 코드는 가격 0·빈 차트 반환 가능 |
| `KIS_REAL_APP_KEY`, `KIS_REAL_APP_SECRET` | 순위 조회 | 순위가 빈 배열로 반환될 수 있음 |
| `GEMINI_API_KEY` | 백엔드 설문 분석 | 관련 기능 별도 확인 필요. 기본 로그인·종목 DB 조회와 분리 |

빈 KIS 값으로 기본 가입·로그인·DB 종목 검색을 먼저 확인할 수 있다. 실제 시세 확인에는 백엔드 담당자와 모의/실전 키 설정을 맞춘다. 키는 서버 측에만 설정한다.

현재 백엔드 `.env.example`에는 `app/config.py`에 없는 `KIS_ACCOUNT_NO`가 있고 순위용 실전 키 항목이 빠져 있다. 그대로 복사했다면 `KIS_ACCOUNT_NO`를 제거하고 위 설정과 비교한다. 알 수 없는 `.env` 필드로 설정 검증 오류가 날 수 있다.

### B-4. 테이블과 종목 데이터 준비

**앞에서 생성한 빈 개발 DB를 가리키는지 확인한 뒤** 기존 마이그레이션을 적용한다.

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m alembic heads
```

`current`와 `heads`의 revision이 일치하는지 확인한다. 작성 시점 head는 `2622474e79f5`이며, 팀의 후속 변경에 따라 달라질 수 있다. 신규 설치를 위해 `revision --autogenerate`로 init 파일을 다시 만들지 않는다. 기존 마이그레이션에는 테이블 삭제·외래키 교체가 포함되므로 데이터가 있는 공용 DB에 이 절차를 그대로 적용하지 않는다.

`backend` 폴더에서 개발 DB에 종목 시드를 적용한다.

```powershell
psql -h localhost -U gp_dev -d gp_dev -v ON_ERROR_STOP=1 -f ..\item_master_seed.sql
psql -h localhost -U gp_dev -d gp_dev -c "SELECT symbol_code, name FROM item_master WHERE symbol_code = '005930';"
```

저장소의 시드는 대표 종목 30개이며 전체 시장 종목 목록이 아니다. 중복 코드는 건너뛰도록 되어 있다. 순위 API에서 나온 종목이 개발 DB에 없으면 상세 조회는 404가 될 수 있다. 전체 종목 적재는 백엔드 담당자와 맞춘다.

### B-5. 백엔드 실행

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

`http://localhost:8000/`와 `http://localhost:8000/docs`를 연다. 실행 터미널은 오류 로그 확인을 위해 유지한다. `/`가 성공해도 7절의 인증·종목 조회까지 확인해야 DB 연결을 검증할 수 있다.

### B-6. 프론트 연결 변경

터미널 2에서 `Stockmaster/frontend/.env`를 수정한다.

```dotenv
VITE_API_BASE_URL=http://localhost:8000/api
VITE_ENABLE_ORDER_SUBMISSION=false
```

`Stockmaster/frontend`에서 실행한다.

```powershell
npm.cmd ci
npm.cmd run dev
```

배포 서버에 로그인했던 상태라면 로그아웃하고 로컬 DB에 가입·로그인한다. 이후 5~7절을 동일하게 진행한다. 백엔드 `.env` 변경 후에는 백엔드도 재시작한다.

## 9. 증상별 점검표

| 증상 | 우선 확인할 것 |
|---|---|
| `npm ci` 실패 | 현재 폴더에 `package.json`과 잠금 파일이 있는지, Node 버전, 설치 오류 원문 |
| 프론트는 열리는데 `localhost:8000` 연결 거부 | 방법 A라면 `.env` 주소 오류, 방법 B라면 백엔드 프로세스·포트 |
| 가입 400 | 응답의 중복 아이디·이메일 메시지. 이미 가입됐다면 로그인 시도 |
| 401 | 해당 서버 계정으로 다시 로그인. 토큰 만료·서명키 변경·다른 DB 계정 여부 |
| 비로그인 403 `Not authenticated` | 인증 헤더 없음. CORS 오류와 별개 |
| 422 | Response의 `detail`에서 잘못된 필드·형식 확인 |
| 종목 상세 404 | DB 종목 시드와 코드 확인 |
| 시세·차트 500 | 백엔드 예외 로그, KIS 모의 키·토큰 발급·외부 응답 확인 |
| 응답 대기 후 시간 초과 | 프론트는 60초 제한. 서버 시작 지연·DB·외부 API 지연을 로그로 구분 |
| `서버에 연결할 수 없습니다` | Request URL, Console의 CORS/연결 오류, 실패 요청의 서버 로그 확인 |
| OPTIONS 실패 | 실제 프론트 origin, 요청 메서드·헤더의 CORS 허용 확인 |
| OPTIONS 성공인데 GET 실패 | 실제 GET 처리·인증·서버 오류 응답의 CORS 헤더까지 확인 |
| HTTPS 프론트에서 HTTP API 차단 | Mixed Content 여부. 접근 가능한 HTTPS API 주소 사용 |
| 로컬 백엔드 설정 검증 오류 | `backend`에서 실행했는지, `.env` 필수값·알 수 없는 키 확인 |
| DB 접속/테이블 오류 | PostgreSQL 실행·접속값·개발 DB 생성·마이그레이션 결과 확인 |
| pull 후에도 예전 화면 | 공유자 push 여부·브랜치·커밋, 실행 중인 폴더, 의존성 설치·재시작 확인 |

느린 요청 안내 배너가 표시돼도 서버가 잠들었다는 확정 증거는 아니다. 계속되는 실패를 단순히 기다리면 해결된다고 판단하지 않는다.

## 10. 백엔드 담당자에게 전달할 기록

아래 양식을 복사하고 Network와 서버 로그로 확인한 사실만 채운다.

```text
[연동 오류 확인 요청]
실행 방식: A 배포 서버 / B 로컬 서버
프론트 브랜치·커밋:
백엔드 배포 버전 또는 로컬 커밋:
프론트 주소(origin):
API 서버 주소:
발생 시각 및 시간대: 예) 2026-09-08 15:20 KST
로그인 / users/me 성공 여부:
화면·재현 순서:
종목코드:
실패 메서드·경로:
HTTP 상태 코드: 없으면 응답 없음으로 기재
Response 또는 Console 오류: 민감정보 제거
같은 API의 Swagger 실행 결과:
요청 사항: 해당 시각의 서버 예외 로그 및 외부 API 실패 원인 확인
```

관심종목·차트 오류라면 백엔드 담당자는 `/price`·`/chart` 요청 로그, KIS 모의 토큰 발급 응답, KIS 오류 코드/메시지, 오류 응답의 CORS 헤더를 확인한다. 현재 토큰 캐시는 프로세스 메모리이며 동시 발급 방지 처리가 없다. 관련 제한이 발생했는지는 로그로 확인해야 하며, 이 구조만으로 이번 장애 원인이라고 단정하지 않는다.

## 11. 다른 PC 연결과 프론트 배포 시 주의점

각자의 `localhost`는 자기 컴퓨터다. 팀원 B의 프론트에서 A의 백엔드에 연결하려면 A의 접근 가능한 IP/주소가 필요하다. A의 개발 서버 바인딩, 방화벽, 같은 네트워크 여부, 실제 프론트 origin에 대한 CORS를 함께 맞춰야 한다. 화면 확인만 필요하면 방법 A가 간단하다.

설치 없이 URL로 공유하려면 프론트도 배포해야 한다. 프론트 빌드 환경의 `VITE_API_BASE_URL`을 설정하고 백엔드가 배포된 프론트 origin을 허용해야 한다. 값 변경 후에는 다시 빌드·배포한다. SPA 배포에서는 `/trading` 같은 경로 새로고침이 `index.html`로 연결되도록 호스팅 설정도 필요하다. 본 문서 작업에서 실제 배포는 하지 않았다.

## 12. 검증 기록과 완료 체크리스트

작성 전 확인한 배포 응답은 다음과 같다. 특정 시점의 읽기 전용 확인이며, 이후 서버 상태와 다른 origin까지 보장하지 않는다.

| 확인 | 결과 | 의미 |
|---|---|---|
| 서버 `/` | 200, status ok | 웹 서버 응답 |
| 비인증 `/api/stocks/005930/price` | 403, Not authenticated | 비로그인 접근 제한 |
| `/api/stocks/005930/chart?period=D` OPTIONS, Origin `http://localhost:5173` | 200, origin 허용, authorization/content-type 허용 | 해당 origin·요청의 사전 확인 성공 |
| 같은 차트 경로 비인증 GET, Origin 포함 | 403, Allow-Origin `*` | 비인증 오류 응답의 CORS 헤더 확인 |
| 인증 후 실제 현재가·차트 | 미검증 | 테스트 계정으로 위 절차 수행 필요 |
| 새 로컬 백엔드·DB 설치 | 미검증 | 문서 명령은 코드·설정과 대조했으며 실제 설치 성공을 보장하는 기록은 아님 |

프론트에서 기존 빌드·린트·자동 테스트 14개가 통과했지만, 자동 테스트는 실제 배포 서버의 로그인·시세 성공을 검증하지 않는다. 팀원이 코드 검사도 실행하려면 `frontend`에서 다음 명령을 사용한다.

```powershell
npm.cmd run lint
npm.cmd test
npm.cmd run build
```

실제 연동 확인 결과는 항목별로 남긴다.

- [ ] 공유받은 프론트 브랜치·커밋과 실행 코드가 일치한다.
- [ ] Network의 API 주소가 선택한 서버와 일치한다.
- [ ] 회원가입 또는 기존 계정 로그인과 `/users/me`가 성공한다.
- [ ] 본인 계좌가 조회된다.
- [ ] `005930` 검색·상세 정보가 조회된다.
- [ ] 관심종목 현재가에 실제 응답 값이 표시된다.
- [ ] 차트 API의 유효한 데이터가 차트에 표시된다.
- [ ] 홈 순위 3개 영역을 확인했다. 빈 응답이면 원인을 따로 기록했다.
- [ ] 미구현 상단 지표와 비활성화 주문을 조회 장애와 구분했다.
- [ ] 실패 항목은 요청 경로·상태·시각·Swagger 비교 결과를 기록했다.
