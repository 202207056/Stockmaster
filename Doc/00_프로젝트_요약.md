## 2. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 한 줄 정의 | 한국투자증권 Open API로 **실제 시세**만 받아오고, 계좌·주문·체결·자산은 **전부 자체 구현**한 모의투자 + 경제학습 플랫폼 |
| 문제의식 | 기존 HTS는 초보자에게 너무 복잡하고, 기존 모의투자는 체험에서 끝나 **왜 손해를 봤는지 배우는 과정이 없음** |
| 목표 시점 | 2026년 11월 중순 완성 (남은 기간 약 12주) |

### 차별점

| # | 기능 | 내용 |
|:--:|---|---|
| 1 | **손실 → 학습 트리거** | 손실이 나면 원인과 관련된 개념 카드를 자동으로 노출 |
| 2 | **도움말 아이콘 ⓘ** | 어려운 용어 옆에서 바로 뜻·예시 확인 |
| 3 | **AI 투자 코치** | 설문 성향과 실제 매매 행동의 불일치를 짚어 줌 |

### 방학 중 확정된 변경 — KIS는 시세 전용

| 구분 | 범위 | 이유 |
|---|---|---|
| KIS Open API (읽기만) | 현재가 · 호가 · 봉 · 지수 · 랭킹 | 사용자마다 실제 증권 계좌가 필요해 주문 API는 사용 불가 |
| **자체 구현 (전부)** | 회원 · 계좌 · 주문 · **체결** · 잔고 · 손익 | 체결 이벤트를 직접 잡아야 "손실 → 학습" 연결이 성립 |
| 결론 | **모의 체결 엔진 = 백엔드의 심장** | 이 프로젝트에서 가장 중요하고 가장 어려운 부분 |

## 3. 현재 진행 상황

### 진척도 — **전체 약 45~50%**

| 영역 | 완성도 | 된 것 | 안 된 것 |
|---|:--:|---|---|
| 프론트엔드 | 45% | 기반·화면 완성 | **실데이터 연동 0%** |
| 백엔드 | 55% | 엔드포인트 27개 동작 | **거래 로직 치명 결함 4건** |
| 데이터베이스 | 55% | 12개 테이블 운영 | 체결·학습·관심종목 테이블 |
| KIS 연동 | 50% | 토큰 캐시·현재가·차트 | 시세 캐시·유량제한·폴백 |
| 학습 시스템 | 25% | 프론트 용어집 66개 | DB·API 전무 |
| AI 기능 | 10% | 설문 저장 | AI 서버 미구축 → 4개 엔드포인트 503 |
| 인프라 | 60% | 백엔드 배포 | 프론트 미배포, CI 없음 |
| 테스트 | 0% | ─ | 전부 |

## 6. 세부 개발 완료 기술

### 백엔드

| 기술 | 핵심 |
|---|---|
| 레이어드 아키텍처 | HTTP(routers) / 로직(services) / DTO(schemas) / ORM(models) / 공통(utils) 분리 |
| JWT 인증 | bcrypt 해싱 + HS256 토큰, `get_current_user` 의존성 주입으로 보호 라우트 처리 |
| 소유권 검증 | 모든 계좌·주문 조회에 로그인 사용자 필터를 빠짐없이 적용 |
| **KIS 토큰 23시간 캐시** | 요청마다 발급하면 즉시 차단되는 함정을 회피 |
| Alembic 실운영 | 테이블 rename(FK 재연결 포함) · 컬럼 타입 변경을 마이그레이션으로 반영 |
| 장애 격리 | 뉴스 크롤링이 실패해도 빈 배열을 반환해 서버 전체가 죽지 않음 |

### 프론트엔드

| 기술 | 핵심 |
|---|---|
| Tailwind v4 `@theme` | **한국 관례(상승=빨강 / 하락=파랑)** 를 토큰에 고정하고 브랜드색과 채도 분리 |
| API 클라이언트 | env 기반 baseURL · 토큰 자동 첨부 · FastAPI `detail`을 사용자 문장으로 정규화 |
| 401 자동 로그아웃 | 응답 인터셉터 → 토큰 삭제 → 커스텀 이벤트 → `AuthContext` 수신 |
| 콜드스타트 대응 | Render 15초 지연용. **진행 중 요청 수를 세어** 동시 요청이 서로의 타이머를 덮어쓰지 않게 처리 |
| 기능 플래그 | `REQUIRE_AUTH` 한 값으로 "로그인 없이 둘러보기" 전체를 토글 |
| HelpIcon + 용어집 | 용어 66개 · 카테고리 7종 · 용어 간 연결. API가 생기면 훅만 교체 |
| 호가 단위 검증 | 가격대별 틱(1~1,000원) + 현재가 ±30%. 백엔드 결함을 입력 단계에서 방어 |
| 설문 성향 산출 | 6문항 × 4선택지 × 0/5/10/15점 규칙 판정 (서버 미구현분 임시 대체) |
| 접근성 | 등락에 색상 + `▲▼` 병기(색약 대응) · 금액 타입 혼재 방어 |

## 7. 난해한 기술

| 영역 | 난이도 | 왜 어려운가 |
|---|:--:|---|
| **모의 체결 엔진** | ★★★ | 주문·체결·포트폴리오·예수금을 **한 트랜잭션 안에서** 갱신해야 함 · 동시 주문 시 `FOR UPDATE` 행 잠금이 필요한데 순서를 틀리면 교착 · `locked_cash`가 없으면 예수금 초과 매수가 반드시 발생 · 체결가는 서버가 KIS 시세로 결정해야 하므로 캐시가 전제 |
| **정확한 회계** | ★★★ | 총자산은 시세가 계속 변해 저장할 수 없고 조회 시 계산해야 함(저장했다가 랭킹이 거꾸로 나온 것이 현재 결함) · 전량 매도 시 행을 지우면 실현손익이 사라져 `trades` 필수 · 랭킹은 일별 스냅샷 + 배치로 우회 · 금액은 전 구간 `Decimal` |
| **KIS API 운영** | ★★ | 3초 폴링 × 사용자 10명이면 즉시 한도 초과 → 캐시 + 레이트 리미터 · **발표일이 휴장일이면 시연 불가** → `LIVE/REPLAY/MOCK` 폴백 · 순위 TR이 실전 계좌 전용이라 예수금 0원 + 주문 TR 차단으로 운용 |
| **손실 → 학습 트리거** | ★★ | 체결 순간 손실 원인을 규칙으로 분류해 개념과 연결 · 체결 엔진·`trades`·학습 콘텐츠가 **모두 끝나야** 착수 가능해 의존성이 가장 길고, 발표 핵심 차별점이라 일정 위험도가 가장 높음 |
| **AI · LLM** | ★★ | 출력 형식이 매번 달라져 JSON 강제 + 스키마 검증 + 재시도 필요 · 죽어도 화면은 살아야 하므로 규칙 기반 폴백을 먼저 구현 · 종목 추천·주가 예측은 정확도 방어가 불가능해 범위 제외 |
| **프론트엔드** | ★ | 캔들 차트는 `lightweight-charts` 필요 · 시세 폴링은 탭 비활성 시 중단이 없으면 요청 폭증 · 비로그인 열람의 이원 렌더링을 전 화면에 일관 유지 |
