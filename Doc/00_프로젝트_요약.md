## 1. 프로젝트 개요

### 한 문장

**한국투자증권 Open API로 실제 시세를 받아오되, 계좌·주문·체결·자산은 전부 자체 구현한
모의투자 플랫폼**이며, 여기에 **AI 성향 분석과 "손실이 나면 학습으로 연결"되는 경제 학습 기능**을
붙인 서비스입니다.

### 왜 만드는가

주식 투자 인구는 늘었지만 기존 HTS/MTS는 초보자에게 지나치게 복잡하고, 기존 모의투자
서비스는 "체험"에서 끝나 **왜 손해를 봤는지 배우는 과정이 없습니다.** 이 프로젝트는
투자 경험과 학습을 한 화면 안에서 잇는 것을 목표로 합니다.

### 차별점 3가지

| # | 기능 | 설명 |
|:--:|---|---|
| 1 | **손실 → 학습 트리거** | 특정 종목에서 일정 이상 손실이 나면 원인과 관련된 개념 카드를 자동으로 띄웁니다 |
| 2 | **도움말 아이콘(HelpIcon)** | 화면 곳곳의 어려운 용어 옆 ⓘ 를 누르면 그 자리에서 뜻·예시가 뜹니다 |
| 3 | **AI 투자 코치** | 설문 성향과 실제 매매 행동의 불일치를 짚어 주는 리포트 |

### 핵심 설계 결정

```text
KIS Open API  →  현재가 · 호가 · 봉 · 지수 · 랭킹        (읽기 전용)
자체 구현      →  회원 · 계좌 · 주문 · 체결 · 잔고 · 손익  (전부)
```

KIS의 모의투자 **주문 API는 쓰지 않습니다.** 사용자마다 실제 증권 계좌가 필요해 불가능하고,
체결 이벤트를 가로챌 수 없어 "손실 → 학습" 연결이 성립하지 않기 때문입니다.
→ 따라서 **모의 체결 엔진이 이 프로젝트 백엔드의 심장**입니다.

### 팀 구성

| 파트 | 담당 |
|---|---|
| 팀장 · DB | 김재표 |
| 백엔드 | 김동휘, 장성우 |
| 프론트엔드 | 이시영 |
| AI | 김진표, 권영준 |

## 4. 세부 개발 완료 기술

### 백엔드

| 기술 | 구현 내용 |
|---|---|
| **레이어드 아키텍처** | HTTP(routers) / 로직(services) / DTO(schemas) / ORM(models) / 공통(utils) 분리 |
| **JWT 인증** | bcrypt 해싱 + HS256 토큰 발급, `get_current_user` 의존성 주입으로 보호 라우트 처리 |
| **소유권 검증** | 모든 계좌·주문 조회에 `Account.user_id == 로그인 사용자` 필터를 빠짐없이 적용 |
| **KIS 토큰 캐시** | 접근토큰을 **23시간 재사용**. 요청마다 발급하면 즉시 차단되는 함정을 회피 |
| **Alembic 마이그레이션** | 테이블 rename(FK 재연결 포함) · 컬럼 타입 변경을 실제 운영 반영 |
| **크롤링 실패 격리** | 뉴스 수집이 실패해도 빈 배열을 반환해 서버 전체가 죽지 않음 |

### 프론트엔드

| 기술 | 구현 내용 |
|---|---|
| **Tailwind v4 `@theme` 토큰** | 색상·폰트를 CSS 변수로 정의해 유틸리티 클래스로 자동 생성. **한국 증시 관례(상승=빨강 / 하락=파랑)** 를 토큰 레벨에 고정하고, 브랜드색(인디고)과 하락색(파랑)의 채도를 분리 |
| **API 클라이언트** | `baseURL`을 `VITE_API_BASE_URL`에서 주입, 요청 인터셉터가 토큰 자동 첨부 |
| **401 자동 로그아웃** | 응답 인터셉터가 401을 잡아 토큰 삭제 → `auth:unauthorized` 커스텀 이벤트 → `AuthContext`가 수신해 로그인 화면으로 유도 |
| **콜드스타트 안내** | Render 무료 티어의 15초 지연에 대응. **진행 중 요청 수를 카운트**해 3초 이상 지연 시 배너를 띄우고, 마지막 요청이 끝나야 내림(동시 요청이 서로의 타이머를 덮어쓰는 문제 해결). 앱 진입 시 서버 워밍업 요청 별도 발사 |
| **에러 문구 정규화** | FastAPI의 `{detail: "..."}` 문자열/배열 형태와 네트워크 오류·타임아웃을 모두 사용자용 한 문장으로 변환 |
| **기능 플래그** | `REQUIRE_AUTH` 한 값으로 "로그인 없이 둘러보기" 전체를 켜고 끔. 라우트 구조는 이미 `ProtectedRoute`로 감싸 두어 다른 파일 수정 불필요 |
| **HelpIcon + 용어집** | 용어 66개를 카테고리 7종으로 분류, `related`로 용어 간 연결. 화면 6곳에 배치. 나중에 `/learn/glossary` API가 생기면 훅만 교체하면 되도록 호출부를 분리 |
| **호가 단위 검증** | 가격대별 틱(1~1,000원) 계산 + 현재가 ±30% 범위 검증. 백엔드 결함을 프론트가 입력 단계에서 방어 |
| **설문 성향 산출** | 6문항 × 4선택지 × 0/5/10/15점 = 0~90점 규칙 기반 판정. 서버가 성향 결과를 만들지 못하는 상태에서 화면을 완성하기 위한 임시 구현 |
| **금액 포맷 방어** | 백엔드가 금액을 문자열/숫자로 뒤섞어 반환하는 문제에 대응하는 `format.js` |
| **접근성** | 등락 표시에 색상 + `▲▼` 기호를 함께 출력해 색약 사용자도 구분 가능 |
| **아이콘 통일** | 이모지 → lucide-react 선 아이콘. `currentColor`를 따르므로 선택 상태에 따른 색 변화 표현이 가능 |

## 5. 난해한 기술 (구현 난이도가 높은 부분)

### 5-1. 모의 체결 엔진 — 이 프로젝트에서 가장 어려움 ★★★

주문 하나가 들어오면 **주문 · 체결 · 포트폴리오 · 예수금 · 원장을 하나의 트랜잭션 안에서**
동시에 갱신해야 합니다. 어느 하나라도 어긋나면 "있지도 않은 돈으로 산 주식"이 생깁니다.

| 어려운 지점 | 내용 |
|---|---|
| **동시성** | 브라우저 탭 두 개에서 동시에 주문하면 두 요청이 모두 잔고 검사를 통과합니다. `SELECT ... FOR UPDATE`로 계좌 행을 잠가야 하는데, 잠그는 순서를 틀리면 교착(deadlock)이 발생합니다 |
| **예수금 잠금** | 미체결 주문이 생기면 `locked_cash`로 돈을 묶어야 합니다. 이 개념을 빼면 예수금보다 많이 사는 버그가 **반드시** 생깁니다 |
| **체결가 결정** | 클라이언트가 보낸 가격을 믿으면 안 됩니다. 서버가 KIS 시세를 조회해 시장가/지정가를 판정해야 하는데, 그 조회가 곧 외부 API 호출이라 **캐시가 전제**됩니다 |
| **거래 규칙** | 호가 단위 · 상하한가 · 장 운영시간 · 거래정지 종목 검증이 전부 필요합니다 |

→ `09_모의체결엔진_설계.md` (3단계 개선안 + 테스트 시나리오 12종)

### 5-2. 정확한 회계 ★★★

| 어려운 지점 | 내용 |
|---|---|
| **총자산 정의** | `총자산 = 현금 + Σ(보유수량 × 현재가)`. 현재가가 계속 변하므로 **저장하면 안 되고 조회 시 계산**해야 합니다. 저장했다가 랭킹이 거꾸로 나온 것이 현재 결함 C-3입니다 |
| **실현손익** | 전량 매도 시 포트폴리오 행을 지우면 "얼마에 사서 얼마에 팔았는지"가 사라집니다. 별도 `trades` 테이블이 반드시 필요합니다 |
| **랭킹 계산** | 매 요청마다 전체 사용자의 시세를 조회하면 KIS가 즉시 차단합니다. **일별 스냅샷 테이블 + 배치**로 우회해야 합니다 |
| **부동소수점** | 금액을 `float`으로 다루면 잔고가 미세하게 어긋납니다. 전 구간 `Decimal` 사용이 원칙 |

### 5-3. KIS Open API 운영 ★★

| 어려운 지점 | 내용 |
|---|---|
| **유량 제한** | 프론트가 3초마다 폴링하고 사용자가 10명이면 즉시 한도 초과입니다. TTL 5초 시세 캐시 + 레이트 리미터가 필요합니다 |
| **폴백 모드** | **발표일이 휴장일이거나 장 마감 후면 시연 자체가 불가능합니다.** `LIVE / REPLAY / MOCK` 3종 모드를 두고 `.env` 하나로 전환할 수 있어야 합니다 |
| **실전 계좌 사용** | 순위분석 TR이 실전 계좌에서만 제공됩니다. 실전 앱키를 쓰되 **예수금 0원 · 주문 TR 코드 차단**으로 사고를 원천 차단합니다 (`08` 문서) |
| **TLS 검증** | 현재 인증서 오류 우회를 위해 `verify=False` 상태이며, 이 경로로 APP KEY/SECRET이 흐릅니다 |

### 5-4. 손실 → 학습 트리거 ★★

체결이 일어나는 **순간** 손익을 평가해, 손실 원인(과도한 집중 · 손절 미실행 · 잦은 매매 등)을
규칙으로 분류하고 그에 맞는 개념 카드를 연결해야 합니다.
체결 엔진 · `trades` 테이블 · 학습 콘텐츠 세 가지가 **모두 완성된 뒤에야** 붙일 수 있어서
의존성이 가장 깁니다. 발표에서 약속한 핵심 차별점이므로 일정상 가장 신경 써야 할 항목입니다.

### 5-5. AI · LLM 연동 ★★

| 어려운 지점 | 내용 |
|---|---|
| **비결정성** | LLM은 같은 입력에도 다른 형식으로 답합니다. JSON 강제 출력 + 스키마 검증 + 재시도가 필요합니다 |
| **폴백 필수** | AI 서버나 LLM이 죽어도 화면은 살아 있어야 합니다. 규칙 기반 점수 산출기를 **먼저** 만들어 폴백 겸 검증 기준으로 씁니다 |
| **비용 · 지연** | 호출당 비용과 수 초의 지연이 발생합니다. 결과 캐싱과 월 예산 상한이 필요합니다 |
| **범위 관리** | 종목 추천·주가 예측은 정확도를 방어할 수 없어 **범위에서 제외**하고, "학습 주제 추천"으로 성격을 바꾸는 것이 팀 결론입니다 |

### 5-6. 프론트엔드 ★

| 어려운 지점 | 내용 |
|---|---|
| **캔들 차트** | 일반 차트 라이브러리로는 봉·거래량·이동평균 조합이 어렵습니다. `lightweight-charts`(TradingView 오픈소스) 도입 예정 |
| **실시간 시세** | 폴링 주기 관리 + 탭 비활성 시 중단(Page Visibility API)이 없으면 요청이 폭증합니다 |
| **비로그인 열람 모드** | 같은 화면에서 "공개 정보는 보이고 개인 자산은 안내로 대체"되는 이원 렌더링을 모든 페이지에 일관되게 유지해야 합니다 |
