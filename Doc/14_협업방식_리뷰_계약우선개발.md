# 14. 협업 방식 리뷰 — 계약 우선(Contract-First) 개발

> 팀이 정한 작업 방식에 대한 평가와, 지금 시점에 맞게 조정할 점
> 작성 2026-08-25

---

## 0. 팀이 정한 방식

```text
1단계  Pydantic으로 데이터 양식(약속) 정의        → schemas/ = API 명세서
2단계  가짜 데이터(Mock)를 뱉는 껍데기 API 구현    → 내부 로직은 비워둠
3단계  명세서를 프론트에 전달 → 병렬 개발
         프론트: 가짜 API로 요청하며 UI/UX에 100% 집중
         백엔드: 같은 시간에 진짜 로직(DB INSERT, KIS 연동) 완성
```

## 결론부터

**방식 자체는 정확합니다.** 업계에서 Contract-First / API-First 라 부르는 표준 패턴이고,
6명이 4개 파트로 나뉜 이 프로젝트에는 특히 잘 맞습니다.
실제로 이 방식 덕분에 백엔드 27개 엔드포인트와 `demo.html`이 나왔습니다.

다만 **지금 시점에서 두 가지를 조정해야 합니다.**

| # | 조정할 점 | 이유 |
|:--:|---|---|
| ① | **프론트는 이제 Mock이 아니라 배포된 실제 API를 써야 합니다** | 2단계는 이미 지났습니다. 실제 API가 돌아가는데 가짜를 쓰면 손해입니다 |
| ② | **1단계(계약)가 절반만 적용되어 있습니다** | 31개 엔드포인트 중 19개가 응답 스키마 없이 나갑니다 |

---

## 1. 이 방식이 옳은 이유 (계속 유지할 것)

### 1-1. 병렬 개발이 실제로 작동했습니다
백엔드가 KIS 연동·DB 붙이는 동안 프론트가 대기하지 않았습니다. 이건 명확한 성과입니다.

### 1-2. 계약이 버그를 미리 막습니다 — 실제 사례
현재 백엔드의 치명적 결함 중 하나(C-2, 음수 수량으로 잔고 증식)는
**1단계에서 계약을 제대로 정의했다면 애초에 생기지 않았을 버그**입니다.

```python
# 현재 (계약이 느슨함)
quantity: int = Field(..., description="주문 수량")
order_type: str = Field(..., description="주문 타입 (매수, 매도)")

# 계약을 제대로 썼다면
quantity: int = Field(..., gt=0, description="주문 수량")          # ← 음수 차단
order_type: Literal["매수", "매도"]                                 # ← 오타 차단
```
Pydantic은 **문서이자 동시에 검증기**입니다. `description`만 채우고 제약을 안 걸면
문서 기능만 쓰고 검증 기능은 버리는 셈입니다.

### 1-3. 6명이 같은 화면을 안 봐도 됩니다
`frontend/README.md`에 이미 도메인별 담당이 나뉘어 있고, 계약이 있으면
서로의 코드를 읽지 않고도 작업이 맞물립니다.

## 2. 지금 발견된 문제 — 계약이 절반만 지켜지고 있습니다

### 2-1. 🔴 응답 스키마 미적용: 31개 중 19개

`response_model`을 지정하지 않으면 **FastAPI가 그냥 dict를 그대로 내보내고,
Swagger에는 응답 형태가 빈칸으로 표시됩니다.**

| 라우터 | 엔드포인트 | `response_model` 적용 |
|---|:--:|:--:|
| `auth.py` | 4 | **4** ✅ |
| `accounts.py` | 3 | **3** ✅ |
| `orders.py` | 3 | 2 🟡 |
| `securities.py` | 4 | 2 🟡 |
| `ai.py` | 7 | 1 🔴 |
| `community.py` | 6 | **0** 🔴 |
| `news.py` | 2 | **0** 🔴 |
| `portfolio.py` | 1 | **0** 🔴 |
| `ranking.py` | 1 | **0** 🔴 |
| **합계** | **31** | **12 (39%)** |

**프론트 입장에서 이게 왜 문제인가**
`https://gp-mock-inv.onrender.com/docs`를 열어 `/api/trading/portfolio`를 보면
**Response 예시가 비어 있습니다.** 명세서 역할을 못 합니다.
결국 프론트는 백엔드 소스를 직접 읽거나, 호출해 보고 눈으로 확인해야 합니다.
**이건 3단계("명세서 보고 작업")가 성립하지 않는다는 뜻입니다.**

### 2-2. 🔴 만들어 놓고 안 쓴 스키마

`app/schemas/portfolio.py`에 이미 이런 스키마가 **정의되어 있습니다.**

```python
class PortfolioItemResponse(BaseModel):
    portfolio_id: int
    symbol_code: str
    security_name: str
    avg_price: Decimal
    hold_quantity: int
    current_price: Decimal | None       # 현재가
    profit_loss: Decimal | None         # 평가손익
    profit_loss_rate: float | None      # 수익률
```

그런데 `routers/portfolio.py`는 이 스키마를 **import조차 하지 않고** 손으로 만든 dict를 반환합니다.
게다가 그 dict에는 `current_price`·`profit_loss`·`profit_loss_rate`가 **없습니다.**

> **1단계 산출물이 2·3단계로 이어지지 않은 전형적인 사례입니다.**
> 프론트는 "명세서에 `profit_loss`가 있네" 하고 UI를 만들었는데
> 실제 응답에는 없는 상황이 벌어집니다. 계약 우선 개발이 실패하는 가장 흔한 방식입니다.

### 2-3. 🟠 같은 개념의 타입이 엔드포인트마다 다릅니다

| API | 금액 필드 | 타입 |
|---|---|---|
| `/trading/accounts` | `balance` | **문자열** `"10000000.00"` |
| `/trading/orders` | `price` | **문자열** `"75000.00"` |
| `/trading/portfolio` | `balance`, `avg_price` | 숫자 `10000000.0` |
| `/stocks/{c}/price` | `current_price` | 숫자 `75000` |

원인: `response_model`을 쓴 곳은 Pydantic이 `Decimal`을 문자열로 직렬화하고,
안 쓴 곳은 코드에서 `float()`로 변환했기 때문입니다.

프론트는 **매번 `Number()`로 감싸야** 합니다. 계약이 있는데도 계약이 통일되지 않은 사례입니다.

### 2-4. 🟠 명세서 문서와 실제 경로가 다릅니다

| `Doc/05_API_명세서.md` | 실제 |
|---|---|
| `/api/v1/auth/login` | `/api/users/login` |
| `/api/v1/stocks/{s}/quote` | `/api/stocks/{s}/price` |
| `/api/v1/portfolio/summary` | 없음 |

문서와 코드 중 **무엇이 정본인지 팀 내에서 확정되어 있지 않습니다.**

## 3. 지금 시점의 조정안

### 조정 ① — 이미 만들어진 API: 프론트는 Mock 대신 실서버를 쓰세요

```text
원래 계획:  프론트 → http://127.0.0.1:8000 (가짜 응답)
지금 권장:  프론트 → https://gp-mock-inv.onrender.com/api (실제 응답)
```

**왜 실서버가 더 나은가**

| | Mock | 배포된 실서버 |
|---|---|---|
| 응답 형태 | 이상적인 값만 | **실제 타입** (문자열/숫자 혼재까지) |
| 실패 케이스 | 없음 | 잔고 부족, 시세 0, 빈 배열, 401 만료 |
| 지연 | 즉시 | **콜드스타트 15초** — 실제로 대응해야 할 문제 |
| 백엔드 실행 | 필요 | 불필요 (저장소 접근도 불필요) |

Mock으로 만든 UI는 "잘 되는 경우"만 처리하게 됩니다.
**실서버로 만들면 로딩·에러·빈 상태를 처음부터 제대로 만들게 됩니다.**

> 프론트 상세 가이드는 `13_프론트엔드_단독진행_가이드.md`.

### 조정 ② — 아직 안 만든 API: 여기서 이 방식을 제대로 쓰세요

남은 엔드포인트는 **원래 방식(1→2→3)이 정확히 들어맞습니다.**

| 미구현 API | 프론트가 기다리는 화면 |
|---|---|
| `GET /api/trading/portfolio/summary` | 자산 요약 카드 |
| `GET/POST/DELETE /api/favorites` | 관심종목 |
| `GET /api/learn/glossary/{term_id}` | 도움말 아이콘 |
| `GET /api/learn/triggers` | 손실 → 학습 카드 |
| `GET /api/market/indices` | 대시보드 지수 카드 |
| `GET /api/stocks/rankings` | 거래대금·급등락 랭킹 |
| `GET /api/trading/trades` | 체결 내역 |
| `GET /api/stocks/{c}/orderbook` | 호가창 |

**이 8개에 대해 이번 주에 1·2단계만 먼저 하면**, 프론트는 다음 주부터 화면을 만들 수 있고
백엔드는 그 사이 진짜 로직을 채우면 됩니다. 딱 팀이 정한 방식대로입니다.

```python
# app/routers/favorites.py — 2단계 껍데기 예시
from fastapi import APIRouter, Depends
from app.schemas.favorite import FavoriteResponse   # ← 1단계 산출물

router = APIRouter(tags=["관심종목"])

@router.get("", response_model=list[FavoriteResponse], summary="관심종목 목록")
def get_favorites(current_user: User = Depends(get_current_user)):
    """
    ⚠️ MOCK — 실제 DB 연동 전 가짜 응답입니다. (담당: OOO, 예정: 9/20)
    """
    return [
        FavoriteResponse(favorite_id=1, symbol_code="005930", name="삼성전자",
                         current_price=75000, change_rate=1.5),
        FavoriteResponse(favorite_id=2, symbol_code="000660", name="SK하이닉스",
                         current_price=223000, change_rate=-0.8),
    ]
```

## 4. 계약을 실제로 지키기 위한 규칙 (팀 합의 권장)

### R-1. 🔴 모든 엔드포인트에 `response_model` 필수
예외 없이. 이게 없으면 Swagger가 명세서 역할을 못 하고, 3단계가 성립하지 않습니다.
```python
@router.get("", response_model=PortfolioSummaryResponse)   # ← 반드시
```
> 우선 적용 대상: `portfolio.py`, `ranking.py`, `community.py`, `news.py` (현재 0개)

### R-2. 🔴 금액 타입을 하나로 통일
프로젝트 전체에서 **금액은 숫자(number)** 로 통일하는 것을 권장합니다.
```python
# app/schemas/base.py
class MoneyModel(BaseModel):
    model_config = ConfigDict(json_encoders={Decimal: lambda v: float(v)})
```
또는 스키마에서 `float`을 쓰고, 계산은 서버 내부에서만 `Decimal`로 하세요.
(국내주식은 원 단위 정수이므로 `int`도 충분합니다.)

### R-3. 🔴 Mock에도 실패 케이스를 넣기
가짜 데이터가 "성공 케이스"만 주면 프론트가 에러 UI를 안 만듭니다.
```python
@router.get("/{symbol_code}/orderbook")
def get_orderbook(symbol_code: str):
    """MOCK. ?mock=empty 로 빈 응답, ?mock=error 로 오류를 테스트할 수 있습니다."""
    if symbol_code == "999999":
        raise HTTPException(404, "종목을 찾을 수 없습니다.")
    ...
```
> 최소한 **빈 배열 / null / 4xx 에러** 세 가지는 프론트가 미리 볼 수 있어야 합니다.

### R-4. 🟠 Mock임을 명확히 표시
```python
"""⚠️ MOCK — 실제 로직 미구현. 담당: OOO / 완료 예정: 9/20"""
```
Swagger 설명에 그대로 노출되므로 프론트가 "이건 아직 가짜"임을 바로 압니다.
**진짜 로직이 붙으면 이 문구를 지우는 것**이 완료 신호가 됩니다.

### R-5. 🟠 정본은 Swagger, 문서는 목표 스펙
```text
정본(Source of Truth)  = https://gp-mock-inv.onrender.com/docs
목표 스펙 / 설계 논의   = Doc/05_API_명세서.md
```
**계약을 바꿀 때는 코드보다 먼저 Doc/05를 고치고 팀에 공유**하고,
합의된 뒤 코드에 반영하세요. 반대 순서면 프론트가 매번 뒤통수를 맞습니다.

### R-6. 🟡 계약 변경은 "깨는 변경"인지 먼저 판단
| 변경 | 위험 | 처리 |
|---|---|---|
| 필드 **추가** | 안전 | 그냥 하세요 |
| 필드 **삭제·이름 변경** | 프론트 깨짐 | 반드시 사전 공유 |
| **타입 변경** (문자열↔숫자) | 조용히 깨짐 | 가장 위험. 반드시 공유 |
| 경로 변경 | 프론트 깨짐 | 사전 공유 |

> 지금 프론트가 대응해야 할 결함 수정(주문 체결가 서버 결정 등)도
> **응답의 `price`가 "요청한 가격"에서 "실제 체결가"로 의미가 바뀌는 변경**입니다.
> 프론트에 미리 알려주세요.

## 5. 이 방식이 만들 수 있는 함정 (미리 알아둘 것)

### 함정 1 — "Mock에서는 됐는데요"
Mock은 항상 성공하고, 빠르고, 데이터가 예쁩니다. 실제는 아닙니다.
현재 실서버에서 실제로 겪게 되는 것들:

| 실제 상황 | Mock으로는 안 보임 |
|---|---|
| Render 콜드스타트 15초 | 로딩 UI 없이 먹통처럼 보임 |
| KIS 키 문제 시 `current_price: 0` | 0원으로 표시되는 버그 |
| 뉴스 크롤링 실패 시 `[]` | 빈 상태 UI 없음 |
| 토큰 60분 만료 → 401 | 조용히 화면이 깨짐 |
| `balance`가 문자열 `"10000000.00"` | `+` 연산 시 문자열 결합 |

> 그래서 **이미 구현된 API는 실서버로 붙이는 게 낫다**는 조정 ①이 나옵니다.

### 함정 2 — 계약이 문서에만 있고 코드에 없음
지금 `PortfolioItemResponse`가 정확히 이 상태입니다(§2-2).
**Pydantic 클래스를 만드는 것과 `response_model`에 연결하는 것은 다른 일**입니다.

### 함정 3 — 계약이 검증을 안 함
`Field(..., description="...")`만 쓰고 `gt=0`, `Literal`, `max_length`를 안 걸면
**문서는 생기지만 버그는 그대로 들어옵니다.** (C-2가 그 결과입니다.)

### 함정 4 — 진짜 로직이 계약을 벗어남
`create_order`에 진짜 로직을 넣는 과정에서 응답 필드가 바뀌면 프론트가 깨집니다.
→ R-6의 "깨는 변경" 판단을 습관화하세요.
