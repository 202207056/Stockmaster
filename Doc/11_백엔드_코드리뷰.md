### C-1. 주문 가격을 클라이언트가 정한다 — 무한 수익 취약점

`app/schemas/order.py` + `app/services/order_service.py`

```python
class OrderRequest(BaseModel):
    price: Decimal = Field(..., description="주문 단가")   # ← 프론트가 보낸 값
...
total_amount = req.price * req.quantity                    # ← 그대로 신뢰
```

**공격 시나리오** (Swagger에서 30초면 재현 가능)
```
1) POST /api/trading/orders  {"symbol_code":"005930","order_type":"매수","price":1,"quantity":10000}
   → 1만주를 1만원에 매수. 평균단가 1원으로 기록됨
2) POST /api/trading/orders  {"symbol_code":"005930","order_type":"매도","price":500000,"quantity":10000}

가격뿐 아니라 **종목과 무관한 아무 숫자**나 넣을 수 있습니다.

quote = await get_current_price(req.symbol_code)

if req.order_kind == "MARKET":
    fill_price = market_price
else:  # LIMIT
    # 상·하한가 및 현재가 대비 허용 범위 검증
    if not (market_price * Decimal("0.7") <= req.price <= market_price * Decimal("1.3")):
        raise HTTPException(400, "주문 가격이 허용 범위를 벗어났습니다.")
    fill_price = min(req.price, market_price) if BUY else max(req.price, market_price)
```

### C-2. 수량·가격 음수 검증 없음 — 잔고 증식 취약점

`OrderRequest.quantity: int` 에 아무 제약이 없습니다.

```
POST /api/trading/orders  {"order_type":"매수", "price":75000, "quantity":-100}

  total_amount = 75000 * (-100) = -7,500,000
  if account.withdrawable_cash < total_amount:   # 10,000,000 < -7,500,000 → False
      → 검증 통과
  account.withdrawable_cash -= (-7,500,000)      # 잔고가 750만원 증가!
  portfolio.hold_quantity = -100                 # 보유수량 음수
```

**수정**
```python
class OrderRequest(BaseModel):
    price: Decimal = Field(..., gt=0, description="주문 단가")
    quantity: int   = Field(..., gt=0, description="주문 수량")
```
DB 레벨에서도 `CHECK (quantity > 0)`, `CHECK (hold_quantity >= 0)`를 걸어 두세요.

### C-3. `balance`의 의미가 무너져 랭킹이 반대로 나온다

`app/models/account.py`의 주석은 이렇게 정의합니다.
```
balance            = 총 자산 (현금 + 보유 주식 평가금액)
withdrawable_cash  = 매수 가능 현금
```

그런데 `order_service.py`는 매수 시 **두 값을 똑같이 차감**합니다.
```python
account.withdrawable_cash -= total_amount
account.balance -= total_amount          # ← 총자산에서 주식 매입액을 빼버림
```

**결과**: `balance == withdrawable_cash`가 항상 성립 → `balance`는 사실상 현금일 뿐이고,
**보유 주식의 가치가 자산에 전혀 반영되지 않습니다.**

그리고 `ranking_service.py`는 이 `balance`로 수익률을 계산합니다.
```python
profit_rate = (SUM(account.balance) - 10_000_000) / 10_000_000 * 100
```
→ **주식을 살수록 수익률이 마이너스**가 되고, 아무것도 안 산 사람이 1위가 됩니다.
현재 랭킹은 "누가 투자를 안 했나" 순위입니다.

**수정 방향** (둘 중 택1)

| 방안 | 내용 | 권장 |
|---|---|---|
| A | `balance` 컬럼을 **없애고** 현금은 `withdrawable_cash` 하나로 관리. 총자산은 조회 시 `현금 + Σ(보유수량 × 현재가)`로 **계산** | ✅ |
| B | `balance`를 유지하되 매수 시 차감하지 않고, 시세 변동마다 재계산 배치 | ❌ 시세가 계속 변해 관리 불가 |

```python
# 방안 A — 매수
account.withdrawable_cash -= total_amount          # 현금만 차감
# balance는 건드리지 않음 (또는 컬럼 제거)

# 총자산 조회 (portfolio 라우터)
holdings_value = sum(p.hold_quantity * current_price(p.symbol_code) for p in items)
total_asset = float(account.withdrawable_cash) + holdings_value
```
랭킹도 이 `total_asset` 기준으로 바꿔야 합니다. 매 요청마다 전 유저 시세를 조회하면 KIS가
차단되므로, **일별 스냅샷 테이블**(`04` 문서 `account_daily_snapshots`)을 만들어 배치로 적재하세요.

### H-1. 모델(Numeric)과 실제 DB(Integer)가 어긋나 있음

### H-3. KIS 호출에 캐시·유량 제한이 전혀 없음

`/api/stocks/{code}/price`는 요청마다 KIS를 직접 호출합니다.
프론트가 3초마다 폴링하고 사용자가 10명이면 **초당 3~4건**, 대시보드가 랭킹까지 그리면 즉시 한도 초과입니다.

토큰 23시간 캐시는 이미 잘 구현되어 있으니(👏), **같은 방식으로 시세도 캐시**하면 됩니다.

```python
_quote_cache: dict[str, tuple[dict, datetime]] = {}
QUOTE_TTL = timedelta(seconds=5)

async def get_current_price(symbol_code: str) -> dict:
    hit = _quote_cache.get(symbol_code)
    if hit and datetime.utcnow() - hit[1] < QUOTE_TTL:
        return hit[0]
    data = await _fetch_from_kis(symbol_code)
    _quote_cache[symbol_code] = (data, datetime.utcnow())
    return data
```
> 이 10줄이 프로젝트의 생존을 좌우합니다. 상세 전략은 `06` 문서 §5.

## 4. ✅ 잘한 점 (그대로 유지할 것)

1. **레이어 분리가 정석대로** — `routers`(HTTP) / `services`(로직) / `schemas`(DTO) / `models`(ORM) / `utils`(공통).
   3,300줄 규모에서 이 구조를 유지한 것은 학부 팀 프로젝트 기준 상위권입니다.
2. **주석 품질이 매우 높습니다.** ORM이 무엇인지, 의존성 주입이 무엇인지까지 설명되어 있어
   **팀원 인수인계와 심사 설명에 그대로 쓸 수 있습니다.** 이건 자산이니 계속 유지하세요.
3. **KIS 토큰 23시간 캐시** — 초보자가 가장 많이 걸리는 함정(요청마다 토큰 발급 → 차단)을 이미 피했습니다.
4. **`bcrypt==4.0.1` 핀** — passlib 1.7.4와 bcrypt 4.1+ 호환 문제를 알고 고정한 것으로 보입니다. 정확한 판단입니다.
5. **계좌 소유권 검증이 일관됩니다** — 모든 계좌/주문 조회에 `Account.user_id == current_user.user_id`가
   빠짐없이 들어가 있어 남의 계좌 접근이 막혀 있습니다. 흔히 빠뜨리는 부분인데 잘 지켰습니다.
6. **크롤링 실패 시 빈 배열 반환** — 뉴스 실패가 서버 전체를 죽이지 않습니다.
7. **Alembic 마이그레이션 3개를 실제로 운영**한 이력(테이블 rename, 타입 변경 포함)이 있습니다.
8. **실제 배포되어 동작합니다** (Render + Supabase 추정). 27개 엔드포인트가 Swagger로 공개되어 있어
   프론트팀이 지금 바로 붙일 수 있습니다.
9. **`demo.html`(1,090줄)** — 로그인·시세·매매·포트폴리오·랭킹·뉴스·커뮤니티 7개 탭을 갖춘
   단일 파일 데모. **백엔드가 실제로 동작함을 증명하는 강력한 산출물**입니다.

## 5. 수정 우선순위 (2주 계획)

| 순위 | 작업 | 근거 | 예상 |
|:--:|---|---|---|
| 1 | **C-1** 체결가를 서버가 KIS 시세로 결정 | 무한 수익 취약점 | 1일 |
| 2 | **C-2** `gt=0` 검증 + DB CHECK 제약 | 잔고 증식 취약점 | 2시간 |
| 3 | **C-3** `balance` 정리 + 총자산 계산식 수정 | 랭킹이 반대로 나옴 | 1일 |
| 4 | **C-4** `with_for_update()` 적용 | 이중 지출 | 2시간 |
| 5 | **H-3** 시세 캐시 (TTL 5초) | KIS 차단 방지 | 반나절 |
| 6 | **H-1** 모델/마이그레이션 타입 일치 | 데이터 정합성 | 2시간 |
| 7 | **H-2** `verify=False` 환경별 분리 | 키 유출 위험 | 1시간 |
| 8 | **M-1** 저장소 통합 + git 커밋 | 작업물 유실 위험 | 1시간 |
| 9 | **H-5** 수수료/세금/장운영시간 | 리얼리티 + 교육 효과 | 1일 |
| 10 | **H-4** `trades` 테이블 + 실현손익 | 자산 화면의 전제 | 2일 |
| 11 | 테스트 12종 작성 | 위 수정의 회귀 방지 | 2일 |
| 12 | **H-6** 뉴스 파이프라인 재설계 | 약관 + AI 연계 | 2일 |

> 1~4번은 **모두 합쳐 3일이면 끝나고, 프로젝트의 신뢰도를 결정합니다.** 다른 신규 기능보다 먼저 하세요.

## 6. 프론트엔드 통합 관련 (중요)

현재 프론트엔드가 **두 벌** 존재합니다.

| | `frontend/` (React) | `gp-mock-inv/demo.html` |
|---|---|---|
| 기술 | React 19 + Vite + Tailwind | 단일 HTML + 바닐라 JS |
| 화면 | 시안 수준, 데이터 연동 0% | 7개 탭 전부 실제 API 연동 |
| API 주소 | `http://localhost:8000` (경로 규약도 불일치) | `https://gp-mock-inv.onrender.com` |

### ⚠️ 반드시 맞춰야 할 것: API 경로 규약
`frontend/README.md`와 `Doc/05_API_명세서.md`는 `/api/v1/...`을 전제로 쓰여 있는데,
실제 백엔드는 `/api/users`, `/api/trading/orders`, `/api/stocks` 입니다.

**권고: 실제 구현된 백엔드 경로를 정본으로 채택하세요.** 이미 배포되어 동작하는 쪽을 기준으로
`Doc/05_API_명세서.md`를 수정하는 것이 맞습니다. 문서 때문에 동작하는 코드를 바꾸는 것은 낭비입니다.

### `demo.html`의 활용법
버리지 말고 **레퍼런스 구현 + 백업 시연 수단**으로 유지하세요.
- React 화면을 만들 때 "이 API를 이렇게 호출하면 된다"는 정답지 역할
- React 통합이 늦어질 경우 **심사 당일 백업 데모**
- 다만 최종 산출물은 React여야 하므로, `demo.html`의 `api()` 함수 로직을
  `frontend/src/api/*.js`로 옮기는 작업부터 시작하면 빠릅니다.
